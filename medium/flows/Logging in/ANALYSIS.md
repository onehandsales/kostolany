## 2. 플로우 목적과 연결

가입 화면의 Sign in에서 공급자 선택·이메일 입력·코드 검증·홈 복귀까지 확인한다.

코드 요청·입력은 보이나 만료·오류·재전송 결과와 서버 세션은 미수록이다.

- 상위 흐름: 없음. Gummble의 최상위 흐름이다.
- 하위 흐름: 없음.
- 폴더 위치: `medium/flows/Logging in`
- 부모·자식은 Gummble 탐색 분류다. 모든 자식 흐름이 반드시 실행되는 순차 단계나 런타임 화면 트리를 뜻하지 않는다.

### 진입 조건과 확인된 종료 범위

- 진입: 가입 화면의 Sign in에서 공급자 선택으로 이동한다.
- 종료: 이메일·코드 입력 뒤 Home이 수록된다. 빈 코드 화면의 sign up 문구는 불일치다.
- 관련 흐름: [Onboarding](<../Onboarding/ANALYSIS.md>) · [Logging out](<../Profile/Settings/Logging out/ANALYSIS.md>)
- 관련 흐름 링크는 기능의 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

- [Sign in or sign up to Medium](https://help.medium.com/hc/en-us/articles/115004915268-Sign-in-or-sign-up-to-Medium): 앱 이메일 인증은 6자리 코드와 Validate를 사용하며 로그인 링크를 받는 대안도 안내한다. 비밀번호는 지원하지 않는다. 링크의 2시간·일회 사용 규칙을 코드의 만료 시간으로 그대로 적용하지 않는다. 캡처에는 Receive a login link 선택지가 없다. 화면에서 관찰한 값·메뉴와 문서에 없는 세부 상태는 구분한다. 미수록 오류·권한·실패 분기는 아래 질문으로 남긴다.

- [API 검토](<../../SOURCES.md#api>). 이 흐름의 내부 endpoint·요청·응답·DB 스키마는 확인하지 않았다.

## 7. 데이터 모델링 시사점

다음은 관찰에 기반한 구현 후보다. Kostolany의 기능 채택·스키마·업무 정책으로 확정하지 않는다.

- 단계 01: 인증 공급자 선택과 기존 세션 유무를 별도 상태로 다룬다.
- 단계 02: 인증 수단과 계정 연결
- 단계 03: 로그인 이메일 입력과 인증 요청
- 단계 04: 인증 요청 대상 이메일
- 단계 05: 인증 대기·코드 입력·재전송 상태를 분리한다.
- 단계 06: 일회용 인증 도전과 로그인 세션 분리
- 단계 07: 피드 항목·기사·작성자·집계 및 사용자 추천 피드백 분리

## 8. 미확인 사항과 검토 질문

**원본에 없는 분기·남은 범위:** 잘못된 이메일·미가입 계정·코드 만료/오입력/재전송·소셜 취소·세션 재진입.

- 단계 01: 각 공급자의 인증 완료·취소·오류 결과는 이 화면에 없다.
- 단계 02: 공급자별 실제 OAuth 경로
- 단계 03: 이메일 형식 검증·계정 없음 처리
- 단계 04: 전송 성공·이메일 소유권 미확인
- 단계 05: 발송 성공·만료 시간·재전송 제한은 화면만으로 알 수 없다.
- 단계 06: 만료·오입력·재전송 제한·세션 생성 결과
- 단계 07: 추천 알고리즘·개인화 저장·카드 전체 클릭 영역
- 같은 계정·같은 빌드에서 시작 상태를 맞춘 뒤 정상·취소·실패·재진입 결과를 검증해야 한다.
