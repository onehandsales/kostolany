# RSS·AI 콘텐츠 처리

기준일: 2026-11-20. [공통 적용 기준](../COMMON/ENGINEERING_RULES.md)과 [트랜잭션 규칙](TRANSACTION.md)을 따른다. 단계·필드 이름은 계약을 위한 설명이며 현재 실행 파이프라인이 아니다.

## BE-PIPE-001 — 수집 입력과 출처 추적

**대상:** 국내외 RSS 공급처 등록, 항목 수집, 원문 확보와 정규화.

RSS에서 수집한 사실을 출처와 함께 보관하고, 하나의 사건에 대해 4단계 설명·예시를 생성한다. 모바일 사용자는 저장·게시된 콘텐츠를 읽는다. 피드 조회 때마다 RSS나 AI를 호출하지 않는다.

공급처·모델·수집 주기·비용 한도는 아직 미정이다. 국내외 뉴스 수집을 무제한 수집·전량 발행으로 해석하지 않고 초기 공급처, 선별 기준과 처리량을 정한다.

### 처리 순서

1. 등록한 RSS 공급처를 읽고 제목·원문 URL·게시 시각·외부 식별자를 정규화한다.
2. 공급처별 GUID·정규화 URL 등 합의한 기준으로 중복을 판정한다.
3. 사용할 수 있는 원문·요약·발췌 범위를 확인하고 생성 입력을 구성한다.
4. 영속적인 생성 작업을 확보하고 DB 트랜잭션 밖에서 AI를 호출한다.
5. 공통 사실, 출처, 4단계 본문과 수준별 예시를 구조적으로 검증한다.
6. 짧은 트랜잭션으로 생성 결과를 저장하고, 별도 발행 조건을 충족했을 때만 공개 버전을 전환한다.
7. 실패는 원인·재시도 가능 여부를 남기고 재처리한다.

RSS에 본문 전체가 없으면 읽지 못한 원문을 읽은 것처럼 생성하지 않는다. 확보한 입력 범위와 출처를 기록한다. 원문·이미지의 저장·재배포 가능 범위는 공급처별로 확인한다.

| 기록 | 구현 기준 |
| --- | --- |
| 공급처·항목 식별 | 공급처 ID, 외부 GUID 또는 합의한 대체 키; URL 정규화 규칙과 버전 |
| 시각 | 원문 게시·수정 시각, 수집 시각을 구분; 원문에 없는 시각을 추정값으로 숨기지 않음 |
| 확보 범위 | 제목·요약·발췌·본문 중 실제 확보한 범위, 원문 URL과 입력 버전/해시 |
| 중복·수정 | 같은 항목의 재수집은 중복 생성하지 않음; 본문 변경은 새 입력 버전과 재생성 정책으로 처리 |
| 요청 제한 | 공급처별 timeout, 크기·redirect·호출 수·동시 처리 제한과 파싱 실패 분류 |

외부 URL은 허용한 scheme·host·port와 경로 정책으로 검증한다. redirect의 매 단계와 실제 연결 주소에서 loopback·사설망·link-local·metadata endpoint 등을 차단한다. XML parser의 외부 entity·외부 DTD 해석을 비활성화하고 압축 해제 후 크기도 제한한다. 원문을 신뢰할 수 있는 도구 명령으로 실행하지 않는다.

**금지·예외:** URL의 host 문자열만 검사한 뒤 임의 redirect를 따라가지 않는다. 공급처의 잘못된 항목 때문에 전체 배치를 유실시키지 않고 항목별 실패를 기록한다. 허용 공급처 추가는 입력 검증을 우회하는 예외가 아니다.

**검증·완료:** 중복 GUID·URL 변형·수정 기사·본문 없는 RSS·잘못된 XML·과대 응답·내부 주소 redirect를 fixture/stub으로 검증한다. 허용된 입력만 저장되고 출처와 확보 범위를 추적할 수 있어야 한다.

## BE-PIPE-002 — 생성 계약과 콘텐츠 품질

**대상:** AI 생성 요청, 네 수준의 결과, 코스톨라니 근거 자료와 재생성.

- 원문 URL, 공급처, 원문 게시 시각, 수집 시각을 구분한다.
- 제목·본문 등 외부 콘텐츠를 프롬프트의 지시문으로 취급하지 않는다. 기사 속 명령이 시스템 규칙이나 도구 권한을 바꿀 수 없게 한다.
- URL 수집은 허용한 공급처·경로 범위와 timeout·크기 제한을 적용한다. redirect를 포함해 내부 네트워크나 임의 파일 접근을 허용하지 않는다.
- 모델·프롬프트 버전·입력 식별자·생성 시각·결과 상태·사용량을 기록한다.
- 4단계별 사실·수치를 서로 다르게 만들지 않는다. 공통 사실을 바탕으로 난이도와 예시를 바꾼다.
- JSON 형태, 필수 단계, 본문·예시 누락, 출처 연결을 검증한다. 파싱 성공이 사실 정확성의 증명은 아니다.
- 책의 실제 근거가 없는 문장에 특정 권·페이지·직접 인용을 붙이지 않는다.
- 품질은 프롬프트를 개선하며 높인다. 프롬프트 변경 전후를 같은 뉴스 샘플로 비교할 수 있게 한다.

- 생성 입력에는 공통 사실·출처 목록·확보 범위·설명 수준·편집 지침·사용한 철학 근거의 식별자와 버전을 연결한다. 책 원문·발췌가 제공되지 않았으면 학습 완료로 기록하지 않는다.
- 결과는 사실 요약, 해석·시나리오, 살펴볼 지표·반대 근거, 수준별 설명·예시와 출처를 구분한다. 실제 필드와 필수 여부는 콘텐츠 계약으로 확정한다.
- 달걀 사이클 등은 판단 근거와 다른 해석 가능성을 설명하는 틀로 사용한다. 모델의 위치 판정을 사실이나 가격 예측 보장으로 저장하지 않는다.
- 생성 모델·공급자·요청 ID(제공 시)·프롬프트/근거 버전·입력 해시·완료 시각·사용량·실패 분류를 실행 기록에 남긴다. 생성 원문 보관은 접근·기간 정책을 가진 저장소에서 처리한다.
- 검증은 구조 검사, 공통 수치·출처 연결 검사, 문체·난이도·근거 적합성 평가로 나눈다. 사람 검수의 필요 여부와 자동 발행 범위는 별도 정책이며, 구조 검사 통과를 사실 정확성 판정으로 취급하지 않는다.

**금지·예외:** 모델이 만든 페이지·인용·근거 식별자를 검증 없이 신뢰하지 않는다. 모델 오류를 고치기 위한 무제한 재생성을 하지 않는다. 검증 실패는 실패 유형과 재시도 예산을 적용한다.

**검증·완료:** 고정된 뉴스 샘플에 정상·수치 불일치·출처 누락·수준 누락·지시문 삽입·잘못된 JSON을 포함한다. 프롬프트 변경 시 같은 샘플로 결과·차이·수용 기준을 기록하고, 자동 검증 가능한 항목과 편집 판단을 구분한다.

## BE-PIPE-003 — 생성·편집·발행 버전의 분리

**대상:** 초안 저장, 운영자 편집, 게시·수정·재생성·공개 중단.

4단계가 모두 준비된 콘텐츠만 게시하는 것을 기본안으로 한다. 일부 단계만 먼저 공개할지는 별도 제품 정책이다. 검증 실패한 출력을 성공으로 간주하지 않는다.

프롬프트를 수정했다고 이미 게시된 콘텐츠 전체를 즉시 덮어쓰지 않는다. 대상·버전·게시 반영 시점을 정해 재생성하고, 실패한 재생성 때문에 기존 정상 콘텐츠를 잃지 않게 한다.

작업 실행 상태와 콘텐츠 공개 상태는 별도로 관리한다. `생성 성공`은 `공개 완료`를 뜻하지 않는다. 구현 전 상태 전이표에 현재 상태·행위자·행동·선행 조건·다음 상태·변경 버전·실패 결과를 작성한다.

| 상황 | 반드시 보장할 결과 |
| --- | --- |
| 최초 생성 | 공개 권한·발행 조건 확인 전에는 초안 결과로 보관 |
| 운영자 수정 | 작성자·편집자·변경 버전 기록; 동시 수정 충돌 검사 |
| 게시 | 공개 버전과 필요한 본문·공개 시각/상태를 같은 트랜잭션에서 전환 |
| 게시 후 재생성 | 새 초안 버전으로 저장; 현재 공개 버전은 새 발행 전까지 유지 |
| 늦게 도착한 AI 결과 | 현재 작업 소유권·기준 콘텐츠 버전을 확인; 최신 수동 편집을 덮어쓰지 않음 |
| 발행 실패 | 기존 공개 버전 보존; 재시도 대상과 실패 이유를 조회 가능하게 기록 |

**예외:** 부분 수준 발행·자동 발행·기존 버전 복구의 허용 조건은 제품 계약에서 정한다. 그 전에는 코드가 임의로 누락된 수준을 다른 수준으로 대체하거나 생성 완료를 공개로 승격하지 않는다.

**검증·완료:** 미게시·실패·과거 비공개 버전은 공개 API에 나타나지 않는다. 새 버전 발행 실패와 늦은 생성 응답에서도 이전 정상 콘텐츠와 최신 편집이 보존되어야 한다.

## BE-PIPE-004 — 작업 소유권·재처리·비용 제한

**대상:** 스케줄러·생성 worker·수동 재처리와 서버 종료·재시작.

초기에는 한 서버의 스케줄러와 DB 작업 테이블로 시작할 수 있다. 상태 이름·스키마는 구현 전 정한다.

- 작업 확보는 원자적이어야 한다. 배포 중 프로세스가 겹쳐도 같은 작업을 무제한 중복 처리하지 않는다.
- 처리 중 서버가 종료된 작업을 회수할 수 있도록 lease·만료·재처리 기준을 둔다.
- 결과 저장 시 현재 작업 소유자·실행 버전을 확인해 오래된 실행이 최신 결과를 덮어쓰지 않게 한다.
- timeout·429·일시적 서버 오류에는 제한된 재시도를 적용한다. 인증 오류·잘못된 입력은 원인 수정 없이 반복하지 않는다.
- AI 요청의 응답을 잃으면 실제 과금·실행 여부를 확신할 수 없을 수 있다. DB 결과의 중복 방지와 공급자 중복 과금 가능성을 구분한다.
- 최대 재시도 이후의 실패 기록과 수동 재처리 방법을 제공한다. 별도 관리자 웹은 필요 시 나중에 결정한다.
- outbox·큐·별도 worker는 장애 복구와 부하 문제가 요구할 때 도입한다.

작업 레코드는 논리 작업 ID, 입력/콘텐츠 기준 버전, 실행 소유자와 실행 번호, lease 만료, 시도 횟수, 다음 실행 시각, 최종 오류 분류를 식별할 수 있어야 한다. 필드명과 상태 이름은 구현 계약에서 정한다.

| 설정 | 구현 전 정할 값과 동작 |
| --- | --- |
| 실행량 | 공급처·모델별 동시 작업 수, 배치 크기, 대기 작업 상한 |
| 호출 시간 | 연결/응답 timeout과 전체 작업 deadline, lease 연장·회수 기준 |
| 재시도 | 오류별 허용 횟수, 지수 대기·jitter·최대 대기, 공급자 Retry-After 반영 범위 |
| 비용 | 작업별 토큰/출력 상한, 기간별 사용량·비용 한도, 한도 도달 시 보류/중단 처리 |
| 복구 | 만료 작업 회수, 최종 실패 조회·수동 재시도 권한, 서비스 종료 시 새 작업 중단과 진행 작업 처리 |

한도는 실제 공급자·예산에 맞춰 숫자와 단위로 설정한다. 모델·worker가 각자 무제한 재시도하지 않도록 재시도 소유자를 정한다. 재처리에서도 새로운 실행 기록을 남기고 원래 실패 기록을 지우지 않는다.

**금지·예외:** 큐·worker 증설을 작업 소유권 검증의 대체로 사용하지 않는다. 동일 입력의 DB 중복 방지와 외부 실행의 정확히 한 번 수행을 혼동하지 않는다.

**검증·완료:** 두 worker의 동시 claim, lease 만료 후 회수, 회수 전 실행의 늦은 저장, 호출 제한, 비용 한도 도달, 프로세스 종료 후 재시작을 검증한다. 반복 실행 후 공개 결과의 중복과 상태 역전이 없고, 실패·보류 작업을 식별해 재처리할 수 있어야 한다.
