# 트랜잭션·동시성 규칙

기준일: 2026-11-20. 예외와 설계 기록은 [공통 규칙](../COMMON/ENGINEERING_RULES.md)을 따른다.

## BE-TX-001 — 유스케이스별 원자성 경계

**대상:** DB를 변경하거나 같은 시점의 일관된 읽기가 필요한 application 작업.

트랜잭션 경계는 application service가 소유한다. Controller와 순수 domain 정책에서 시작하지 않는다. Spring이 관리하는 동일 DataSource·transaction manager에 참여하는 JPA/JDBC 작업을 원자적으로 묶는다.

Supabase에 PostgreSQL이 있다는 사실은 이 원칙을 바꾸지 않는다. Spring이 JDBC로 접속하므로 일반 PostgreSQL과 같은 방식으로 트랜잭션을 관리한다.

| 작업 | 트랜잭션 관계 |
| --- | --- |
| 같은 업무 흐름의 JPA 저장·갱신 | 같은 transaction manager에 참여하면 함께 커밋·롤백 |
| Supabase Auth HTTP 요청 | JDBC 트랜잭션에 포함되지 않음 |
| Supabase Storage 업로드·삭제 | JDBC 트랜잭션에 포함되지 않음 |
| RSS·AI HTTP 호출 | JDBC 트랜잭션에 포함되지 않음 |
| 별도 thread·프로세스의 작업 | 기존 imperative 트랜잭션 자동 전파 없음 |

### 어노테이션과 실패 전파

- `org.springframework.transaction.annotation.Transactional`을 사용한다. 이름은 `@Transaction`이 아니다.
- 쓰기 메서드의 경계를 명시하고, 필요한 읽기 서비스에는 `@Transactional(readOnly = true)`를 사용한다.
- Spring proxy를 통과하는 공개 메서드 호출을 기본으로 한다. 같은 객체 내부에서 다른 `@Transactional` 메서드를 호출하는 self-invocation에 의존하지 않는다.
- annotation이 있는 클래스를 직접 `new`로 만들어 트랜잭션이 적용됐다고 가정하지 않는다.
- 기본 전파 `REQUIRED`를 출발점으로 한다. `REQUIRES_NEW`는 외부 작업의 롤백과 다른 커밋이 필요한 이유 및 연결 풀 영향을 검토한 경우에만 사용한다.
- 별도 설정이 없으면 Spring 기본 롤백은 `RuntimeException`·`Error` 기준이다. checked exception까지 롤백해야 하면 `rollbackFor` 또는 프로젝트 전역 정책을 명시하고 테스트한다.
- 예외를 잡아 성공처럼 반환하면 원래 의도한 롤백이 되지 않을 수 있다. 실패를 정상 응답으로 숨기지 않는다.
- `readOnly`는 사용자 권한 검증이나 모든 쓰기 차단을 대신하지 않는다.

각 쓰기 유스케이스의 계약에 다음을 기록한다.

| 항목 | 필수 내용 |
| --- | --- |
| 진입점 | application 메서드, 호출 주체, 검증된 사용자와 권한 |
| 원자적 변경 | 같은 커밋에 포함되는 테이블·상태·집계·작업 기록 |
| 불변식 | 성공 후 반드시 맞아야 할 관계와 수치 |
| 실패 | 어느 저장에서 실패해도 남지 않아야 할 변경과 별도로 남길 실패 기록 |
| 충돌 | 중복·동시 수정 판정 키, 충돌 처리, 잠금 순서 |
| 외부 작업 | 커밋 전후 실행 순서, 외부 성공 후 DB 실패 시 복구 |
| 제한 | 적용할 트랜잭션·쿼리·잠금 대기 시간과 선택 이유 |

**예외:** 같은 객체의 직접 호출 대신 별도 Spring bean이나 명시적 `TransactionTemplate` 경계를 사용할 수 있다. 사용 이유와 동일 원자성을 확인하는 테스트가 필요하다. 기본 롤백 정책을 변경하면 RuntimeException과 필요한 checked exception의 실제 동작을 모두 검증한다.

**검증·완료:** 실제 Spring bean을 호출하고 별도 트랜잭션에서 성공 커밋과 실패 롤백을 관측한다. 테스트 자체의 자동 롤백이나 어노테이션 존재 여부만으로 완료 처리하지 않는다.

근거: [Spring @Transactional](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html), [롤백 규칙](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/rolling-back.html).

## BE-TX-002 — 외부 호출과 영속적인 후속 작업

**대상:** RSS·AI·Auth·Storage 등 네트워크 호출을 포함하는 작업.

콘텐츠 생성은 다음 흐름을 기본안으로 한다.

```text
짧은 트랜잭션: 생성 작업 확보·상태 기록
        ↓ commit
트랜잭션 밖: RSS 본문 확보·AI 호출·응답 검증
        ↓
짧은 트랜잭션: 콘텐츠·수준별 설명 저장 + 작업 성공 상태
```

네트워크 응답을 기다리는 동안 DB 연결·잠금을 오래 잡지 않는다. 생성 실패 상태는 실패한 트랜잭션이 끝난 뒤 별도의 짧은 작업으로 기록한다. 한 클래스의 self-invocation을 피하도록 별도 service 경계나 필요 시 `TransactionTemplate`을 사용한다.

콘텐츠 저장과 후속 작업 전달을 함께 보장해야 한다면 같은 트랜잭션에 작업 행 또는 outbox를 기록한다. 메모리 이벤트나 `afterCommit` callback만으로 서버 장애 시 전달을 보장했다고 하지 않는다. 별도 메시지 브로커는 필수 조건이 아니다.

- 외부 호출 조율 메서드 전체에 DB 트랜잭션을 걸지 않는다. 외부 호출 timeout·전체 작업 제한·재시도 예산을 별도로 정의한다.
- 후속 작업은 소비 완료 전까지 DB에서 재발견할 수 있어야 한다. 소비자가 반복 실행될 수 있으므로 결과 저장의 중복 방지 키와 완료 조건을 둔다.
- 파일 업로드 성공 뒤 DB 저장이 실패하면 업로드 식별자와 고아 파일 회수 방법을 남긴다. DB 롤백이 이미 완료한 외부 요청까지 취소한다고 설명하지 않는다.
- 응답 전송 실패는 DB 롤백의 증거가 아니다. 클라이언트 재시도는 기존 작업 결과를 확인하거나 동일 최종 상태로 수렴시킨다.

**금지·예외:** 외부 응답을 기다리며 행 잠금을 유지하지 않는다. 특수한 연계 요구가 있으면 최대 점유 시간·실패 보상·부하 영향을 설계 기록으로 검증하며, 일반 HTTP 호출을 분산 트랜잭션이라고 취급하지 않는다.

**검증·완료:** 작업 확보 후 종료, 외부 성공 후 저장 실패, 결과 커밋 후 응답 유실을 각각 재현한다. 재실행 후 공개 데이터·작업 상태가 일치하고, 외부 중복 실행·과금 여부가 불명확하면 그 상태를 성공/실패로 임의 확정하지 않는다.

### 원자성 검토의 출발점

| 작업 | 함께 성공해야 하는 범위 |
| --- | --- |
| 콘텐츠 게시 | 공통 기사 정보·필요한 수준별 설명·게시 상태 |
| 좋아요·북마크 등록 | 사용자와 기사에 대한 관계 저장, 저장형 집계가 있으면 집계 일관성 |
| 프로필 초기화 | 인증 사용자와 앱 프로필의 중복 없는 연결 |
| 작업 성공 처리 | 생성 결과와 작업 성공 기록의 불일치 방지 |

여러 기능이 한 작업에 참여하면 조율 owner와 같은 트랜잭션 참여 여부를 계약에 기록한다. 각 repository에서 독립된 새 트랜잭션을 열어 원자성을 깨지 않는다.

## BE-TX-003 — 중복 요청·동시 수정·재시도

**대상:** 반복 가능한 쓰기, 집계 갱신, 생성 작업 확보, 동일 데이터의 동시 편집.

- `이미 존재하는지 조회 → 없으면 저장`만으로 중복을 막지 않는다. 합의된 업무 키에 DB unique 제약을 둔다.
- 좋아요·북마크 등록·해제는 반복 호출해도 동일한 최종 상태가 되도록 설계한다.
- 집계 수를 저장한다면 읽어온 값에 1을 더해 덮어쓰는 방식 대신 원자적 갱신·재계산 등 일관성 전략을 정한다.
- optimistic version·조건부 update·row lock은 실제 충돌 지점에 맞춰 선택한다. 분산 락을 기본 도입하지 않는다.
- 중복 또는 deadlock 후 PostgreSQL 트랜잭션이 실패한 상태에서 계속 쿼리하지 않는다. 필요하면 전체 작업을 경계 밖에서 제한적으로 재시도하거나 적절한 upsert를 사용한다.
- 격리 수준을 일괄 `SERIALIZABLE`로 올리지 않는다. 필요한 불변식과 재시도 비용을 근거로 선택한다.
- 앱이 timeout을 받았어도 서버에서 커밋했을 수 있다. 쓰기 재시도 결과를 계약과 테스트로 확인한다.

| 충돌 종류 | 구현에서 정할 것 | 필수 결과 검증 |
| --- | --- | --- |
| 좋아요·북마크 반복 등록 | 사용자+대상 업무 키의 unique, 이미 존재할 때 응답 | 관계는 1개, 저장 집계가 있으면 1회 반영 |
| 동일 글 동시 편집 | 요청 버전과 저장 버전을 비교하는 조건부 갱신 또는 동등한 제어 | 오래된 요청은 충돌로 반환하고 새 본문을 덮어쓰지 않음 |
| 집계 동시 증가·감소 | 관계 변화가 실제 발생한 경우에만 원자적 갱신 또는 재계산 | 원본 관계와 집계가 합의한 일관성 범위 내에서 일치 |
| 작업 중복 확보 | 상태·기한·실행 소유자를 포함한 원자적 claim | 현재 소유자만 결과를 확정; 과거 실행은 반영 거절 |
| 교착·직렬화 실패 | 해당 오류 분류와 새 트랜잭션에서 전체 단위 재시도 | 제한 내 성공 또는 명시적 실패; 부분 커밋·무한 재시도 없음 |

Idempotency key가 필요한 명령은 `사용자/작업 범위 + 키`, 요청 내용의 fingerprint, 처리 중·완료 상태, 저장할 응답, 만료·보관 기간을 계약에 정한다. 같은 키·다른 내용은 거절한다. 모든 읽기·쓰기에 동일한 키 저장소를 강제하지 않으며, 자연 키와 절대 상태 변경으로 충분한 작업은 그 방식을 사용한다.

재시도는 이를 소유하는 한 계층에서 수행한다. HTTP client·SDK·worker의 중첩 재시도로 횟수가 곱해지지 않게 전체 호출 횟수·대기·deadline을 계산한다. 외부 요청의 재실행 안전성은 DB 재시도와 별도로 판단한다.

**금지·예외:** unique 충돌 후 이미 실패한 PostgreSQL 트랜잭션에서 계속 조회하지 않는다. DB가 보장할 불변식을 프로세스 내 mutex만으로 보장하지 않는다. 비관적 잠금이 필요하면 잠글 행·순서·보유 시간·실패 응답을 기록한다.

**검증·완료:** 두 개 이상의 독립 트랜잭션·연결로 충돌을 실제 발생시키고 모든 작업의 종료를 기다린 뒤 관계 수·집계·버전·응답을 확인한다. 고정 sleep 대신 barrier/latch와 제한 시간을 사용한다. 성공·거절 건수와 최종 상태가 계약과 일치해야 한다.

## BE-TX-004 — 실패 지점별 통합 검증

**대상:** 위 세 규칙이 적용되는 신규·변경 유스케이스.

실제 Spring 서비스 프록시와 격리 PostgreSQL을 사용해 중간 실패의 전체 롤백, 같은 요청 재실행, 동시 중복 요청, 카운터 갱신을 검증한다. 단순히 `@Transactional`이 붙어 있거나 mock 함수가 호출됐다는 이유로 원자성 검증을 완료하지 않는다.

최소한 첫 저장 이후 다음 저장 실패, flush/commit 시점의 제약 실패, 같은 요청 재실행, 권한 거절 후 상태 불변을 적용 가능한 작업마다 검증한다. 별도 실패 기록이 필요하면 업무 변경의 롤백과 실패 기록의 커밋을 각각 확인한다. 실제 커밋 검증은 테스트 외곽의 자동 롤백 트랜잭션으로 가리지 않는다.

**금지·예외:** DB가 필요한 검증을 repository mock·H2 통과로 대체하지 않는다. DB 환경이 없으면 해당 검증은 미실행으로 남기고 완료로 판단하지 않는다.

**완료 조건:** 테스트 이름·대상 계약·실패 지점·예상 저장 상태가 연결되고, 다른 연결에서 관측한 결과가 불변식을 만족한다. 상세 테스트 격리와 실행 기록은 [품질 규칙](../COMMON/QUALITY_AND_WORKFLOW.md)을 따른다.
