# Backend 규칙

기준일: 2026-11-20. [공통 적용 기준](../COMMON/ENGINEERING_RULES.md)을 함께 따른다. 아래는 앞으로의 구현·리뷰 기준이며 현재 서버 구현 완료를 뜻하지 않는다.

## BE-ARCH-001 — 모듈과 계층의 책임

**대상:** 서버 패키지, 공개 서비스, 모듈 간 호출과 외부 의존.

Kotlin + Spring Boot로 하나의 배포 단위를 만든다. 기능별로 책임을 나누는 modular monolith를 기본안으로 한다. 실제 MSA를 구축했다고 표현하지 않는다.

```text
<base-package>/
  account/       # Supabase 신원과 앱 사용자 연결
  article/       # 콘텐츠, 설명 수준, 게시·조회
  reaction/      # 좋아요, 북마크, 조회 이벤트
  ingestion/     # RSS·AI 작업 조율과 재처리
  shared/        # HTTP 오류·보안 설정 등 필요한 공통 기반
```

패키지명과 코드 루트는 초기화 때 고정한다. 각 기능에 필요한 경우 다음 역할을 둔다. 빈 계층을 전부 미리 만들지 않는다.

위 이름은 시작점이다. Medium 사용자 흐름에서 확정한 댓글·팔로우·목록·글쓰기 등의 책임을 단순히 `reaction`에 몰아넣지 않는다. 기능 계약별로 소유 모듈을 정하고 필요해질 때 추가한다.

| 역할 | 책임 |
| --- | --- |
| `api` | Controller, 요청·응답 DTO, 입력 검증과 HTTP 변환 |
| `application` | 사용자 흐름, 권한, 트랜잭션 경계, 외부 작업 조율 |
| `domain` | 프레임워크 없이 검증할 가치가 있는 순수 업무 정책 |
| `infrastructure` | JPA persistence, RSS·AI·Storage adapter |

### 허용되는 의존과 금지되는 의존

- Controller는 application service를 호출한다. 직접 JPA repository나 외부 AI를 호출하지 않는다.
- 같은 기능의 application service가 Spring Data JPA repository를 사용하는 실용적인 구성을 허용한다. 모든 repository에 별도 port를 강제하지 않는다.
- 도메인 정책을 독립시켜야 하는 경우에만 repository port나 별도 domain model을 도입한다. 단순 CRUD에서 JPA entity와 똑같은 객체를 반복 생성하지 않는다.
- 순수 `domain` 정책에는 Spring·JPA·HTTP SDK를 넣지 않는다. JPA entity는 persistence 모델로 구분한다.
- 다른 기능의 repository·entity를 직접 참조하거나 수정하지 않는다. 그 기능이 공개한 application 서비스·query 계약을 사용한다.
- 기능 간 공개 계약과 HTTP 응답에는 JPA entity·Hibernate proxy·Supabase SDK 객체를 노출하지 않는다.
- 여러 기능을 조율할 때 책임자를 하나 정하고 순환 의존을 만들지 않는다.
- RSS·AI·Storage adapter는 공급자별 데이터와 오류를 앱에서 사용하는 결과로 변환한다.
- `shared`를 업무 로직을 모으는 공간으로 쓰지 않는다. 재사용되지 않는 코드는 소유 기능 안에 둔다.

**예외:** 여러 모듈을 조회하는 projection이 실제 쿼리 비용 때문에 필요하면 소유자·읽기 전용 범위·스키마 변경 영향·통합 테스트를 기록한다. 조회 편의를 다른 모듈의 쓰기 허용으로 확대하지 않는다. 예외 기록은 공통 기준을 따른다.

**검증·완료:** 초기화 때 선택한 구조 검사 도구로 Controller의 repository·SDK 직접 의존, 순수 domain의 프레임워크 의존, 모듈 순환, 타 모듈 내부 의존을 검사한다. 허용 예외 외 위반 0건이어야 한다. 공개 계약은 DTO·값 타입으로 구성하고 Entity·lazy proxy가 없는지 직렬화 테스트와 리뷰로 확인한다.

## BE-ARCH-002 — 교체 가능한 경계와 작성자 확장

**대상:** AI·RSS·Storage 어댑터, 콘텐츠 작성자·권한·수준별 설명 모델.

- 외부 호출 계약은 소비하는 application 모듈이 소유한다. 입력·결과·실패를 앱의 타입으로 정의하고 공급자 SDK 타입은 infrastructure에 둔다.
- 공급자별 응답을 공통 결과로 변환하고, 공급자 고유의 기능·실패 정보가 필요하면 명시적 필드나 capability로 표현한다. 지원하지 않는 기능을 빈 성공 결과로 숨기지 않는다.
- 공급자 선택은 구성 지점에서 주입한다. 업무 서비스 곳곳에 공급자 이름별 분기를 만들지 않는다. 공통 계약 테스트를 각 어댑터에 적용한다.
- 초기 작성자 한 명도 앱 사용자 관계로 식별한다. 콘텐츠에 작성자 관계를 두고, 발행 권한과 해당 콘텐츠의 편집 권한은 구별해 검사한다. 계정 ID·이메일을 코드 상수로 넣어 운영자를 판단하지 않는다.
- AI 공급자·생성 실행자와 서비스의 작성자·발행 주체를 구분한다. 네 수준의 본문을 네 명의 작가로 모델링하지 않는다.
- 공통 기사 정보와 수준별 본문·버전을 분리한다. 수준 식별 값·누락 처리·기존 앱 호환성은 계약에서 정의한다. 새 수준 추가 시 DB만 변경하면 된다고 가정하지 않는다.

**금지·예외:** 교체 이유가 없는 단순 CRUD에 동일한 port·adapter·model을 반복 생성하지 않는다. 추상화 도입은 외부 의존 격리, 모듈 공개 계약 또는 독립 정책 검증이라는 이유를 기록한다. 미래 작가의 구체적인 승인 절차와 권한 종류는 제품 계약에서 정한다.

**검증·완료:** 다른 작성자 두 명의 소유권 분리, 발행 권한 없는 사용자 거절, 동일 입력에 대한 어댑터의 공통 성공·실패 계약을 검증한다. 공급자 교체 시 Controller·순수 정책의 공급자 코드 변경이 필요하면 경계를 재검토한다.

## BE-SEC-001 — 인증과 자원별 권한

**대상:** 보호된 API, 개인 데이터, 편집·발행·관리 작업.

1. 모바일이 Supabase Auth에서 발급받은 access token을 Bearer 헤더로 전달한다.
2. Spring Security가 서명·허용 알고리즘·만료·issuer·audience를 검증한다.
3. 검증한 `sub`를 Supabase 인증 사용자 식별자로 사용해 앱 사용자와 연결한다.
4. application service가 해당 작업의 권한과 데이터 소유권을 확인한다.

비대칭 서명 키와 JWKS 검증을 기본안으로 한다. 실제 키 종류를 먼저 확인하고 issuer·JWKS URL·audience를 프로젝트 설정과 맞춘다. legacy HS256 토큰에 JWKS 방식을 그대로 적용하지 않는다.

JWT를 단순 decode한 값, 클라이언트가 보낸 이메일·userId, 수정 가능한 사용자 metadata를 권한 근거로 쓰지 않는다. Supabase의 DB 역할 `authenticated`를 앱 관리자 권한으로 해석하지 않는다.

JWT의 로컬 검증만으로 원격 로그아웃·계정 삭제가 즉시 반영된다고 가정하지 않는다. 즉시 차단이 필요한 작업은 별도 서비스 계정 상태 확인 등 정책을 정한다.

인증 계정과 앱 프로필의 최초 연결은 재시도·동시 요청에도 중복되지 않아야 한다. Supabase Auth 계정 작업과 앱 프로필 쓰기는 하나의 JDBC 트랜잭션이라고 가정하지 않는다.

요청 DTO의 `userId`, `authorId`, 상태·권한 필드를 Entity에 일괄 복사하지 않는다. 수정 가능한 필드를 유스케이스별로 허용하고, 자원 ID를 아는 것만으로 접근을 허용하지 않는다. 목록·상세·내보내기·파일 URL 발급에도 동일한 공개 범위와 소유권 규칙을 적용한다.

**검증·완료:** 토큰 누락·만료·서명 오류·issuer/audience 오류, 다른 사용자의 자원 ID, 권한 필드 주입, 삭제·차단된 계정 정책을 테스트한다. 거절된 요청은 데이터·발행 상태·작업 예약을 변경하지 않아야 한다. 공개 API의 인증 예외는 계약에 명시한다.

근거: [Supabase JWT](https://supabase.com/docs/guides/auth/jwts), [Spring Security Resource Server](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html).

## BE-QUERY-001 — 조회 비용과 응답 경계

**대상:** 목록·상세·검색·집계 조회와 응답 변환.

- 조회는 필요한 컬럼·페이지 범위만 읽는다. 피드에서 본문 4개 전체를 불필요하게 가져오지 않는다.
- JPA entity를 그대로 JSON으로 내보내지 않고 트랜잭션 안에서 필요한 응답 데이터를 구성한다.
- `open-in-view=false`를 기본안으로 하여 응답 직렬화 중 숨은 DB 조회를 방지한다.
- N+1이나 정렬 비용이 확인되면 projection·fetch 전략·인덱스를 검토한다. 캐시를 먼저 붙여 원인을 가리지 않는다.
- 쓰기 흐름의 원자성·중복 요청·동시성은 [트랜잭션 규칙](TRANSACTION.md)을 따른다.
- 생성·수집은 사용자 조회 요청마다 수행하지 않는다. 저장된 게시 콘텐츠를 읽도록 한다.

- 목록은 기본·최대 페이지 크기를 계약에 숫자로 정하고 무제한 조회를 거절한다. 상세는 요청한 설명 수준과 필요한 공통 정보만 반환한다.
- 정렬 동률·null·페이지 경계는 API 계약과 동일하게 구현한다. 인기 점수처럼 값이 변하는 정렬은 허용되는 중복·누락과 snapshot 여부를 별도 정의한다.
- 캐시를 도입하면 공개/개인 데이터, 사용자, 설명 수준, 필터, 콘텐츠 버전이 구분되는 키와 무효화 규칙을 정한다. 권한을 검사하지 않은 개인 응답을 공유 캐시에 저장하지 않는다.

**예외:** 대량 내보내기는 별도 권한·배치 크기·타임아웃·비동기 작업 계약을 가진다. 일반 목록 API의 제한을 해제하는 방식으로 구현하지 않는다.

**검증·완료:** 대표 데이터와 최대 페이지에서 쿼리 수·반환 크기·실행 계획을 확인한다. 목록 길이만큼 추가 쿼리가 증가하는 N+1, 미게시 데이터 노출, 사용자 간 캐시 혼합이 없어야 한다. 성능 수치는 데이터 규모·환경·측정 조건과 함께 기록한다.
