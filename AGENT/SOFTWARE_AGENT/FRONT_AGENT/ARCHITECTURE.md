# 프론트엔드 아키텍처

[규칙 진입점](README.md) · [상태와 비동기](STATE_AND_DATA.md)

## 설계의 출발점

기능을 추가하기 전에 화면 이름보다 사용자 흐름, 데이터 소유자, 상태 수명, 실패 복구 경계를 먼저 정한다. 현재 앱 규모에서 이해하고 수정할 수 있는 가장 작은 구조를 선택한다. 추후 기능을 예상해 빈 디렉터리·범용 프레임워크·추상 클래스를 선행 생성하지 않는다.

| 질문 | 설계에서 답할 내용 |
| --- | --- |
| 무엇이 같은 데이터인가 | 기사 ID, 사용자 범위, 설명 수준, 검색 조건 등의 식별 기준 |
| 누가 변경하는가 | 화면 로컬 상태, 기능별 상태 관리자, 데이터 공급부의 책임 |
| 얼마나 유지하는가 | 렌더·화면·탭·앱 실행·기기 저장 중 어느 수명인가 |
| 어디까지 실패하는가 | 항목·섹션·화면·앱 전체 중 실패 영향과 재시도 단위 |
| 무엇을 복구하는가 | 읽던 목록·입력·스크롤·확정된 상태·전송 대기 의도 |
| 어떻게 검증하는가 | 성공뿐 아니라 경합·응답 역전·실패·이탈 사례 |

## 디렉터리와 의존성

현재 `FE/src`의 `app / features / shared`를 유지한다. 아래는 책임을 설명하는 구조이며 모든 하위 폴더를 지금 만들어야 한다는 뜻이 아니다.

```text
src/
  app/                         # 앱 조립, navigation, 전역 수명의 provider
  features/
    article/                   # 기사 상세와 설명 수준 기능
    feed/                      # 홈 목록 기능
    search/                    # 기사 검색 기능
    <기능>/
      <Feature>Screen.tsx      # 경로와 화면 조립
      components/              # 이 기능에 속한 표현 컴포넌트
      use<Feature>.ts          # 화면 행동과 비동기 상태 연결
      model/                   # 필요할 때만 순수 규칙과 상태 전이 분리
      data/                    # source, fixture, 향후 전송 adapter
      types.ts                 # 기능의 데이터·행동 계약
  shared/
    ui/                        # 업무 기능에 종속되지 않는 UI
    theme/                     # 색상, 간격, 글꼴 등 표현 토큰
    <공통 관심사>/              # 실제 공유 필요가 생겼을 때 추가
```

- `app`은 기능을 조립한다. 기능이 `app`의 navigation 인스턴스·provider 내부를 역참조하지 않는다. 필요한 ID·콜백·인터페이스를 전달한다.
- `features`는 `shared`에 의존할 수 있다. `shared`는 특정 기능의 screen·fixture·store를 import하지 않는다.
- 서로 다른 기능의 결합은 의도를 드러내는 공개 타입·함수로 제한한다. 다른 기능의 내부 reducer·상태 객체를 직접 변경하지 않는다.
- 모든 경로를 `index.ts`로 재수출하지 않는다. 순환 import를 감추는 barrel, `export *` 확산을 피한다. 공개 진입점이 필요한 경계에만 제한적으로 둔다.
- 현재 검색이 피드의 타입·fixture를 사용하는 구성은 기존 구현이다. 중복 소유 문제 없이 작동하는 부분을 이 문서 때문에 전면 이동하지 않는다. 공통 기사 소유권이 실제로 필요해지는 작업에서 소비자·테스트와 함께 경계를 조정한다.
- `utils`, `common`, `manager`, `service`를 분류되지 않은 코드의 보관함으로 사용하지 않는다. `normalizeSearchQuery`, `ArticleSource`처럼 목적을 드러낸다.

## 책임 경계

| 역할 | 책임 | 포함하지 않을 책임 |
| --- | --- | --- |
| Screen | 경로 입력 검증, 화면 조립, 이동·포커스 연결 | HTTP 세부 구현, 여러 화면의 반응 원본 관리 |
| 표현 컴포넌트 | props 표시, 접근성, 로컬 시각 상태, 사용자 의도 전달 | 임의 API 호출, 전역 상태 초기화, 다른 경로 직접 조작 |
| 기능 hook | 사용자 의도와 상태 전이 연결, 구독·정리 | 업무 관계 없는 범용 옵션 수십 개 |
| 순수 규칙 | 입력 검증·정규화·정렬·파생값 계산 | React hook, 시간·네트워크·저장소의 숨은 접근 |
| source/adapter | 데이터 조회·변경 경계, 입력/응답 변환, 오류 분류 | 토스트·모달·navigation 직접 실행 |
| 상태 관리자 | 같은 자원의 일관성, 구독, 변경 수명 | 모든 기능의 임시 입력 보관 |

순수 함수와 함수형 컴포넌트를 기본으로 한다. SDK 인스턴스나 플랫폼 자원 수명 때문에 필요할 때만 클래스를 사용한다. 모든 기능에 controller·repository·use case 계층을 기계적으로 만들지 않는다.

## 상태 소유권

| 상태 | 기본 소유자 | 기준 |
| --- | --- | --- |
| 검색 입력, 접힘 여부 | 가장 가까운 화면/컴포넌트 | 다른 화면과 공유할 이유가 없으면 전역화하지 않음 |
| 검색어·조회 결과·스크롤 복귀 | 해당 탐색 세션 | 상세 진입 때문에 초기화하지 않음 |
| 여러 화면의 같은 기사 반응 | 기능의 공유 자원 상태 | 기사 ID와 현재 사용자 범위로 동일 상태 참조 |
| 설명 수준 선택 | 현재 상세의 UI 상태 | 계정 설정으로 저장하는 정책은 별도 결정 |
| 서버 데이터 | 도입한 query cache 또는 기능 상태 관리자 | 동일 데이터의 수정 권한을 여러 저장소에 중복 부여하지 않음 |
| 인증 세션 | 승인된 인증 adapter | 화면마다 독립 세션·refresh를 만들지 않음 |
| 기기 저장값 | 저장소 adapter | 버전, 초기화·삭제·복원 실패 기준 포함 |

- 계산 가능한 값은 원본에서 계산한다. `isEmpty`를 목록과 별도 state로 저장해 불일치시키지 않는다.
- 공유 상태는 필요한 소비자들의 공통 수명에 둔다. 앱 루트에서 큰 Context 값 하나를 바꿔 모든 기사를 다시 렌더링하는 방식은 구독 범위를 검토한다.
- Context·reducer·외부 store·query library는 대안이다. 사용할 문제, 수명, 구독 비용, 테스트 방법을 설명한 뒤 선택한다.
- 외부 store를 직접 만들 경우 React의 구독 계약을 지키고 동시 렌더 중 다른 스냅샷을 읽는 문제를 검토한다. 모듈 전역 mutable 객체를 화면에서 읽기만 하는 방식은 반응형 상태가 아니다.

## 데이터 계약과 교체 경계

현재는 fixture source를 사용한다. 실제 API 도입 시 [API 계약 규칙](../COMMON/API_CONTRACT.md)을 따른다.

- 화면이 실제 HTTP 응답·DB 컬럼·인증 공급자 타입에 직접 종속되지 않게 한다. 필요한 곳에서 DTO를 기능 모델로 변환한다.
- 의미가 같은 타입을 계층마다 이름만 바꿔 복제하지 않는다. nullable·날짜·enum·식별자 의미가 달라지는 경계에서 변환한다.
- 외부 JSON은 TypeScript 타입 선언만으로 검증되지 않는다. 실제 연동 시 경계에서 런타임 검증을 수행한다. 검증 도구의 도입 여부는 현재 의존성과 요구를 기준으로 결정한다.
- fixture와 실제 source가 성공·빈 값·실패·취소 계약을 공유하도록 한다. fixture만 항상 즉시 성공하는 별도 UI 분기를 만들지 않는다.
- mock의 정렬·초기값·모의 사용자·지연·실패 횟수는 문서에 명시한다. 네트워크 장애가 나면 실제 데이터를 fixture로 조용히 바꾸는 fallback을 만들지 않는다.
- 날짜의 원본 시각과 표시 문자열을 구분한다. 실제 정렬은 계약된 값을 사용하고 locale 문자열을 파싱해 정렬하지 않는다.
- native module·저장소·통신 adapter는 가능하면 교체 가능한 작은 경계를 둔다. React Native 전체를 감싸는 자체 플랫폼 프레임워크는 만들지 않는다.

## 컴포넌트 설계

- 컴포넌트를 나누는 기준은 재사용 횟수만이 아니라 독립된 책임·상태·접근성·검증 경계다.
- 서로 다른 의미의 카드를 boolean props 조합으로 하나에 억지로 합치지 않는다. 공통 출처·썸네일 같은 부분을 공유하고 레이아웃은 별도 컴포넌트로 둘 수 있다.
- 범용 컴포넌트에는 대상 기능의 출처·권한·검색 정책을 하드코딩하지 않는다.
- 업무 컴포넌트는 값과 의도 콜백을 받는다. 부모의 `setState` 전체를 넘겨 내부 구조를 수정하게 하지 않는다.
- 제어형과 비제어형 입력의 소유권을 명확히 한다. 같은 값을 props와 내부 state 양쪽에서 독립적으로 수정하지 않는다.
- 오류 경계는 렌더 실패를 격리하는 수단이다. 비동기 요청·이벤트 핸들러 오류를 모두 잡아준다고 가정하지 않는다. 해당 오류는 작업 경계에서 처리한다.

## 구조 변경과 의존성 도입

기존 해결 방식으로 요구를 충족할 수 있으면 유지한다. 의존성 도입에는 해결할 문제, 설치된 React/Expo/RN 호환성, iOS·Android 지원, native 빌드 영향, 유지보수 상태, 크기·초기화 비용, 라이선스와 대체 가능성을 기록한다.

SDK·navigation 교체, 전역 상태 도구 도입, 공통 모델 이동, 영속 저장 추가는 영향받는 화면과 이전 데이터/상태의 전환 방법을 포함한다. 단순 화면 기능을 이유로 앱 전체를 동시에 리팩터링하지 않는다. 변경을 단계적으로 적용하고 사용되지 않는 이전 구현을 방치하지 않는다.
