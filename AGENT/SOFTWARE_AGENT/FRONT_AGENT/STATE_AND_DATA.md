# 상태·비동기·데이터 규칙

[규칙 진입점](README.md) · [아키텍처](ARCHITECTURE.md) · [검증](TESTING_AND_DELIVERY.md)

## 상태 모델과 불변식

화면의 상태와 데이터 접근 상태를 구분한다. 상태를 추가할 때 어떤 사건으로 들어가고 빠져나오는지, 그동안 무엇을 보여주는지 함께 정한다.

| 상황 | 보여줄 내용 | 유지/제거할 내용 |
| --- | --- | --- |
| 검색 전·공백 입력 | 입력 안내·주제 바로가기 | 검색 요청과 이전 검색 결과 제거 |
| 최초 조회 | 해당 자원의 로딩 | 다른 기사·검색어의 데이터 노출 금지 |
| 조회 성공·0건 | 결과 없음과 다음 행동 | 오류로 표현하지 않음 |
| 조회 실패 | 실패한 범위와 재시도 | 상관없는 본문·탐색 기능 유지 |
| 같은 자원의 갱신 | 기존 데이터와 갱신 상태 | 읽던 콘텐츠·스크롤을 이유 없이 지우지 않음 |
| 다른 기사·검색어·수준 선택 | 새 선택의 상태 | 이전 선택의 내용이 새 결과처럼 보이지 않게 함 |
| 사용자 취소 | 취소 또는 이전 화면 | 취소를 요청 실패 토스트로 표시하지 않음 |
| 연결 끊김·결과 불명 | 확인 가능한 마지막 상태와 복구 행동 | 서버 저장 성공·실패를 추측하지 않음 |

- 가능하지 않은 상태 조합은 타입으로 줄인다. 예를 들어 `status: 'loading' | 'ready' | 'error'`의 판별 union을 사용한다. 항상 모든 기능에 동일한 상태 이름을 강제하지는 않는다.
- 화면에 필요한 데이터와 그 데이터를 요청한 identity를 연결한다. 기사 ID·설명 수준·검색 조건·사용자 범위를 누락하지 않는다.
- 결과 수, 선택 여부, 표시 본문은 같은 상태에서 파생한다. 레이블만 새 검색어이고 목록은 이전 검색 결과인 상태를 허용하지 않는다.
- 숨김과 유지 정책은 기능별로 문서화한다. 설명 수준 변경은 이전 해석을 숨기되 공통 사실 요약을 유지할 수 있다.
- `loading` 플래그 하나로 최초 조회·추가 페이지·갱신·쓰기의 진행 상태를 동시에 표현하지 않는다.

## 조회 요청의 수명

1. 요청 identity와 요청 세대/수명 식별자를 결정한다.
2. 입력이 바뀌면 이전 결과가 현재 화면을 나타내지 못하도록 렌더 단계부터 구분한다.
3. 요청을 시작하고 동기 예외·Promise 실패를 같은 작업 경계에서 처리한다.
4. 응답의 ID·조건과 현재 유효한 요청인지 확인한 뒤 상태에 반영한다.
5. 조건 변경·이탈·공급부 교체 시 타이머·구독을 정리하고 이전 응답의 반영 권한을 끝낸다.

`AbortController` 등 실제 취소 기능을 사용할 수 있으면 활용하되 취소 성공만으로 일관성을 보장하지 않는다. 취소 전 완료했거나 취소를 지원하지 않는 공급부도 있으므로 응답 수명 검사를 유지한다. 화면 전용 요청과 공유 자원의 요청은 취소 책임이 다를 수 있다.

- query 문자열 비교만으로 `A → B → A`의 첫 A와 마지막 A를 구분할 수 없다. 요청 세대, cache의 요청 계약, 컴포넌트 수명 등 선택한 방식으로 검증한다.
- hook 호출부의 `key`에 정리를 의존한다면 그 전제를 문서화하고 재사용 시 안전성을 확인한다. 임의의 호출부에서도 안전한 API가 필요한지 검토한다.
- `isMounted` 하나로 모든 요청을 구분하지 않는다. 여전히 mounted여도 이미 다른 기사·사용자·조건일 수 있다.
- StrictMode 정리 후 재실행, source 함수 교체, 늦은 성공뿐 아니라 늦은 실패도 검증한다.
- 동일한 응답은 재사용할 수 있지만 서로 다른 사용자·수준·언어·정렬의 응답을 같은 cache key로 합치지 않는다.

## 검색·입력과 debounce

입력 원문과 조회용 정규화 값을 분리한다. 입력할 때마다 원문을 강제로 trim·재포맷해 커서와 한글 조합을 깨뜨리지 않는다. 정규화·일치 방식·정렬은 fixture 기본안과 서버 계약을 구분한다.

- debounce는 요청 빈도를 줄이는 기능이며 오래된 응답 차단을 대신하지 않는다.
- 새 입력, 지우기, 이탈 시 예약된 요청을 해제한다. 빈 입력에는 요청하지 않는다.
- 엔터·검색 버튼·주제 선택과 debounce가 같은 요청을 두 번 보내지 않게 한다.
- 정규화 후 같은 조건이라면 불필요한 재조회·스크롤 초기화를 피한다.
- 글자 조합 중 입력, 붙여넣기, 최대 길이, 빠른 지우기와 재입력을 확인한다. 실제 OS IME를 보지 않았다면 검증했다고 기록하지 않는다.

## 쓰기 명령과 연속 조작

조회와 쓰기의 취소·재시도 의미를 구분한다. 화면에서 기다리기를 그만뒀다고 이미 시작한 저장이 취소됐다는 뜻은 아니다.

| 처리 방식 | 사용 조건 | 명시할 제약 |
| --- | --- | --- |
| 처리 중 입력 차단 | 중복 작업의 비용이 크고 다음 입력을 받지 않는 UX가 합의됨 | 비활성·진행 상태를 알림. 마지막 사용자 의도 유지 요구가 있으면 이 방식만으로 충족했다고 하지 않음 |
| 자원별 직렬 처리 + 최신 목표 보관 | 좋아요처럼 최종 목표 상태가 중요한 경우 | 진행 중 명령과 대기 중 최신 의도를 구분, 완료 후 필요한 명령만 전송 |
| 모든 명령을 순서대로 처리 | 각 입력 자체가 의미 있는 누적 업무 | 명령 ID·순서·중복·부분 실패 정책 필요 |
| 병렬 처리 | 계약이 병렬 변경과 버전을 지원함 | 충돌·응답 역전·최종 동기화 규칙 필요 |

한 기능에서 고른 방식을 문서화하고 테스트한다. 좋아요를 누를 때마다 무조건 병렬 요청을 보내고 마지막에 도착한 응답을 신뢰하지 않는다. 서버의 쓰기 처리 순서와 네트워크 응답 도착 순서는 같지 않을 수 있다.

- 등록·해제는 목표 상태를 가진 명령으로 표현한다. 원시 클릭 이벤트와 저장 명령을 분리한다.
- 목표 상태는 사용자 입력 시 결정하고 같은 명령의 재시도에는 그대로 사용한다. retry에서 다시 `!현재값`을 계산하면 사용자의 의도가 뒤집힐 수 있다.
- 재시도에 안전한 명령인지는 실제 API 계약으로 확인한다. 클라이언트에서 이름을 `set`으로 바꾼 것만으로 중복 생성·중복 집계가 해결되지 않는다.
- 자원별 pending 정보를 관리한다. 한 기사 처리 중이라는 이유로 다른 모든 기사까지 잠그지 않는다.
- 실제 저장의 timeout·연결 단절은 서버에 반영됐는지 불명확할 수 있다. 무조건 롤백·무조건 성공으로 확정하지 말고 같은 명령의 멱등 재시도 또는 재조회 등 계약된 방법으로 확인한다.
- 다른 사용자로 전환한 뒤 이전 사용자의 늦은 응답을 현재 상태에 반영하지 않는다. 세션/사용자 세대도 수명에 포함한다.

## 낙관적 갱신과 복구

낙관적 갱신을 채택할 때는 최소한 **마지막 확정 상태**, **현재 사용자 목표**, **진행 중 명령 식별자**를 구분할 수 있어야 한다. 데이터 구조는 기능 규모에 맞게 선택한다.

1. 기준 상태와 명령의 대상·목표·수명을 확보한다.
2. 목표를 화면에 반영하고 진행 중임을 필요에 맞게 알린다.
3. 성공하면 유효한 명령의 확정 상태를 갱신한다. 이후 입력이 있으면 그 목표를 버리지 않는다.
4. 실패하면 해당 명령이 아직 현재 상태를 소유하는지 확인한다. 새 성공을 과거 snapshot으로 되돌리지 않는다.
5. 실패한 범위와 다음 행동을 알리고, 재시도할 명령의 목표를 명확히 한다.

- 응답마다 `count + 1` 또는 `count - 1`을 적용하지 않는다. 확정된 반응 여부와 목표의 차이로 표시 수치를 계산하거나 계약된 절대값을 사용한다.
- 낙관적으로 이미 반영한 증가분을 성공 시 다시 더하지 않는다. 실패해도 다른 기사·다른 명령의 증가분을 빼지 않는다.
- 0 미만이 된 값을 단순 clamp로 가려 논리 결함을 숨기지 않는다. 음수가 발생하지 않는 상태 전이를 검증한다.
- 전체 cache snapshot 복원은 다른 작업을 덮어쓸 수 있다. 변경한 자원·필드·명령 범위로 복구한다.
- 쓰기 이전에 시작한 조회가 쓰기 성공 뒤 도착해 과거 상태를 덮을 수 있다. 취소·버전 비교·유효성 검사·성공 후 재조회 중 실제 계약에 맞는 방식을 사용한다.
- 공유 자원의 확정은 화면 unmount와 별개일 수 있다. 화면을 떠나면 화면 전용 부작용은 중지하되 공유 상태가 영원히 pending으로 남지 않도록 소유자를 정한다.

## 목록·상세·공유 상태

같은 기사 ID와 사용자 범위의 반응은 홈·검색·상세에서 동일한 기준 상태를 읽는다. 목록이 반응 값을 포함하는 별도 응답이라면 병합·무효화 정책을 정한다. query cache와 별도 store에 각각 수정 가능한 반응 값을 중복 보관하지 않는다.

- 상세를 열 때 목록의 오래된 객체 전체를 복사해 반응의 새 원본으로 만들지 않는다.
- 목록 복귀·다른 탭 방문·같은 기사 재진입 후 같은 상태를 확인한다.
- 변경한 항목이 화면 밖에 있어도 다시 나타났을 때 일치해야 한다. 카드 재활용·가상화가 상태를 잃게 하지 않는다.
- 반응 수 변화로 목록 순서가 바뀌는지는 실제 정렬 정책의 문제다. 화면용 숫자 변화 때문에 읽던 목록을 임의로 재정렬하지 않는다.

## 페이지·갱신·cache

- cursor는 불투명 값으로 다룬다. 실제 서버 cursor를 숫자라고 가정해 증가시키지 않는다.
- 같은 query·cursor의 중복 추가 요청을 막고 끝 페이지 조건을 명시한다.
- 목록 교체와 페이지 추가를 구분한다. 새 조건의 첫 페이지에 이전 조건의 다음 페이지가 섞이지 않게 한다.
- 같은 ID가 겹칠 때 병합·중복 제거 기준과 순서 계약을 기록한다. 서버 순서를 임의의 보조 정렬로 바꾸지 않는다.
- stale 시간·갱신 계기·cache 보관 기간은 요구와 데이터 민감도에 맞게 정한다. 매 render·매 focus마다 무조건 전체를 다시 요청하지 않는다.
- fixture에는 실제 네트워크 cache가 없더라도 상태 초기화 시점·실패 이력·mock 인스턴스 수명을 명시한다.

## 오류·재시도·수명 복구

- 사용자 취소, 입력 검증, 권한 거부, 연결 문제, timeout, 형식 불일치, 예상하지 못한 오류를 처리 가능한 범위에서 구분한다. 실제 API가 없으면 HTTP 오류를 확인했다고 쓰지 않는다.
- 오류는 작업 경계에서 UI에 해석 가능한 형태로 바꾼다. 모든 오류를 빈 배열로 변환하거나 catch 뒤 성공 상태로 처리하지 않는다.
- retry 가능 여부·횟수·간격·사용자 수동 재시도와의 관계를 정한다. 입력 오류나 확정된 권한 거부를 무한 재시도하지 않는다.
- 공유 타이머·listener를 중복 등록하지 않는다. 앱이 background에 있을 때 타이머가 계속 정확히 실행된다고 가정하지 않는다. 복귀 때 실제 경과 시간과 유효성을 재평가한다. [RN AppState](https://reactnative.dev/docs/0.86/appstate).
- 영속 상태를 도입하면 schema 버전·만료·사용자 범위·읽기 실패·부분 손상·삭제·migration을 설계한다. cache를 못 읽었다고 앱 전체를 열 수 없게 하지 않는다.
- 앱 종료 후 유지할 정책이 없으면 메모리 상태의 한계를 명시한다. 승인되지 않은 offline 쓰기 queue·동기화 서비스를 미리 추가하지 않는다.

## 최소 경합 검토 사례

| 사례 | 확인할 결과 |
| --- | --- |
| A 조회 → B 조회 → A가 늦게 성공/실패 | B 상태 유지 |
| A → B → A | 마지막 A의 수명과 첫 A 응답 구분 |
| 좋아요 등록 → 해제 → 등록 | 선택한 입력 정책에 따른 최종 목표·수치 일치 |
| 이전 쓰기 실패가 새 성공 뒤 도착 | 새 성공 유지, 과거 snapshot 복구 금지 |
| 이전 조회가 쓰기 성공 뒤 도착 | 확정된 변경을 과거 값으로 덮지 않음 |
| 쓰기 중 상세 이탈·목록 복귀 | 명령 소유자·공유 상태·pending 정리 일치 |
| 재시도 버튼 연타 | 같은 명령의 중복 효과 없음 |
| 사용자/공급부 교체 | 이전 범위 응답 격리 |

이 표는 검증 기준이며 아직 구현하지 않은 Goal의 완료 증거가 아니다. 실제로 적용한 전략과 검증 결과는 해당 작업에서 기록한다.
