# 성능·보안·운영 규칙

[규칙 진입점](README.md) · [상태와 비동기](STATE_AND_DATA.md) · [빌드와 검증](TESTING_AND_DELIVERY.md)

## 성능은 측정과 사용자 행동으로 판단

속도·메모리·화면 반응의 문제를 먼저 재현한다. 테스트 데이터 수, 이미지 크기, 기기·OS, 빌드 모드, cold/warm 조건, 반복 횟수를 기록한다. 고성능 PC의 개발 브라우저 결과를 모바일 성능 수치로 제출하지 않는다.

| 영역 | 확인할 증거 |
| --- | --- |
| 시작 | cold/warm 시작, splash 이후 실제 읽기/조작 가능 시점 |
| 입력·이동 | 입력 반응, 검색 결과 반영, 화면 전환 중 멈춤 |
| 목록 | 긴 목록 스크롤, 빈 영역, 이미지 지연, 항목 재활용 시 상태 오류 |
| 자원 | 화면 반복 진입 후 메모리·listener·타이머 증가, 앱 복귀 후 중복 요청 |
| 통신 | 요청 수·중복·전송 크기·cache·timeout·retry 증폭 |
| 변경 효과 | 같은 조건의 변경 전/후, 개선과 부작용 |

실제 native 성능은 가능한 경우 release 조건에서 측정한다. dev mode의 오버헤드, JS thread 작업, native UI 작업을 구분한다. [RN 성능 지침](https://reactnative.dev/docs/performance).

- 메모이제이션·리스트 교체·native 최적화는 병목 근거를 가진 뒤 적용한다. 측정 없이 “최적화됐다”고 쓰지 않는다.
- 입력 이벤트마다 무거운 전체 검색·정렬·JSON 변환을 반복하지 않는다. 데이터 규모에 따라 사전 계산·작업 분할·공급부 이동을 검토한다.
- 불필요한 root state 변경으로 전체 앱을 다시 그리지 않도록 상태·구독 범위를 좁힌다. selector와 안정적인 snapshot을 사용하고 정확성을 먼저 확인한다.
- 작은 fixture 10개의 성공을 대규모 목록·저사양 기기 성능 증거로 확장하지 않는다. 성능 목표가 필요하면 대상 기기와 흐름에 맞게 설정한다.

## 리스트·이미지·애니메이션

- 긴 동적 목록에는 FlatList 등 가상화를 사용한다. 같은 축의 ScrollView 안에 긴 가상화 목록을 중첩해 가상화를 무력화하지 않는다.
- 안정적인 ID와 필요한 값만 전달한다. 외부 선택 상태 변경이 카드에 반영되는지 확인하고 강제 난수 key로 갱신 문제를 해결하지 않는다.
- `getItemLayout`은 높이를 정확히 알 때만 사용한다. 큰 글자·줄바꿈으로 달라지는 카드에 추정 높이를 고정해 스크롤 오류를 만들지 않는다.
- 렌더 창·batch·초기 항목 수·clipping 조정은 빈 영역·메모리·복귀 동작을 함께 측정한다. 특정 기기에서의 수치를 보편적인 최적값으로 복사하지 않는다.
- 원격 이미지를 도입하면 표시 크기에 맞는 자원, decode 비용, cache 정책, 실패·취소를 다룬다. 원본 대형 이미지와 base64 문자열을 전역 상태에 중복 보관하지 않는다.
- 프리패치는 사용자가 볼 가능성과 자원 한도를 고려한다. 전체 목록을 무제한 사전 다운로드하지 않는다.
- 스크롤·drag의 고빈도 이벤트를 모두 React state로 올리지 않는다. UI/animation 도구의 실행 위치와 지원 속성을 확인한다.
- 애니메이션은 완료·취소·이탈 때 정리한다. 애니메이션 완료 callback을 업무 저장 성공의 근거로 쓰지 않는다.

## 수명·메모리·배터리

- 구독, interval, timeout, animation, network listener의 등록·해제 소유자를 명확히 한다.
- background에서 polling·animation을 계속할 필요가 있는지 확인한다. foreground 복귀 때 여러 화면이 같은 갱신을 중복 실행하지 않게 한다.
- 캐시와 기록의 보관 한도를 둔다. 기사/검색어/이미지를 앱 실행 내내 무제한 쌓지 않는다.
- 대용량 데이터는 필요 없는 참조를 해제한다. 정리 후에도 화면을 다시 열 수 있어야 하며 전역 초기화로 다른 화면의 데이터를 날리지 않는다.
- 성능 검사에는 반복 진입·복귀와 긴 실행을 포함한다. 한 번의 정상 로딩만으로 누수 없음이라고 판정하지 않는다.

## 인증·개인 데이터 — 실제 연동 승인 시 적용

현재 fixture 단계에서는 인증 SDK·실제 계정을 연결하지 않는다. 향후 구조는 Google → Supabase Auth 세션 → Spring 요청에 access token 전달이며, 별도의 앱 자체 JWT 발급 체계를 만들지 않는다. Supabase client로 업무 DB를 직접 조회하는 `supabase.from`은 사용하지 않는다. 파일 기능은 별도 합의된 계약이 있을 때만 도입한다.

- 선택한 SDK 버전의 session·refresh 계약을 확인한다. SDK refresh와 자체 refresh가 중복 실행되지 않게 한다. 시작·복귀·로그아웃·계정 전환·취소를 각각 처리한다. [Supabase RN Auth](https://supabase.com/docs/guides/auth/quickstarts/react-native).
- refresh 요청을 조율하고 재요청 횟수를 제한한다. 갱신 실패·일시 네트워크 오류·세션 확정 만료를 구분한다. 일시 오류만으로 사용자 계정·데이터를 삭제하지 않는다.
- 읽기 재시도와 쓰기 재시도는 다르다. 인증 갱신 후 원래 쓰기를 반복할 때 멱등성 계약과 결과 불명 상태를 확인한다.
- 로그아웃·계정 전환은 사용자별 cache·pending 응답·메모리 데이터·저장값의 경계를 함께 정리한다. 이전 사용자 데이터를 다음 사용자에게 잠시라도 보여주지 않는다.
- 화면에 버튼을 숨기는 것은 권한 검증이 아니다. 서버가 사용자와 자원 접근을 검증해야 하며 UI 테스트를 그 증거로 사용하지 않는다.
- 로그인 후 복귀는 허용된 내부 목적지와 유효한 사용자 의도로 제한한다. 취소·오래된 callback·중복 callback이 자동 작업을 실행하지 않게 한다.

## 저장소·비밀 값·링크

- 앱 번들·공개 환경 변수는 비밀 저장소가 아니다. 서비스 비밀 키·DB 자격 증명·AI 키를 앱에 넣지 않는다.
- token·민감 값에는 Keychain 및 Keystore 기반 암호화 등 지원되는 보안 저장 adapter를 검토한다. Keystore를 임의 문자열 DB로 취급하지 않는다. AsyncStorage에 token을 평문 보관하지 않는다.
- 선택한 adapter의 실제 저장 방식, 크기 제한, 백업·복원, 재설치, 잠금/생체 정보 변경, 읽기·삭제 실패를 확인한다. OS가 민감 값을 영구 보존하거나 자동 삭제한다고 추측하지 않는다.
- 공개 설정·민감 세션·기사 cache를 같은 전역 snapshot으로 통째로 영속화하지 않는다. 데이터 목적과 만료·삭제 범위를 구분한다.
- 외부 URL·deep link·사용자 입력은 신뢰하지 않는다. 허용 목적지·콜백 검증·권한 확인을 거치며 token을 URL·클립보드·알림·로그로 복사하지 않는다.
- WebView를 도입한다면 URL 허용 범위·메시지 검증·스크립트 주입·외부 파일 접근을 따로 설계한다. 요청 범위 밖에서 편의를 위해 추가하지 않는다.
- TLS 검증을 끄거나 임의 인증서를 신뢰하도록 제품 설정을 약화하지 않는다. 인증서 고정은 갱신·복구 비용과 위협 모델을 확인한 뒤 결정한다.

위 보안 경계는 [RN 보안 지침](https://reactnative.dev/docs/0.86/security)을 대조했다. 프로젝트의 저장소·외부 연결 규칙이며 현재 앱에 해당 연동이 구현됐다는 뜻은 아니다.

## 관측·오류 보고

- 오류는 작업명, 실패 단계, 필요한 내부 자원 ID, 요청/명령 correlation ID, 소요 시간, 결과 코드처럼 원인을 좁힐 수 있는 정보로 기록한다. 실제 사용자 식별자 수집은 필요한 최소 범위와 승인된 정책을 따른다.
- token, 이메일/프로필 원문, 검색어 원문, 입력 폼 전체, 응답 본문, 기기 고유 식별자를 기본 로그로 남기지 않는다. 재현에는 비식별 fixture를 사용한다.
- 사용자가 볼 문구, 개발 진단 코드, 공급자 오류 원문을 분리한다. 원시 stack trace를 제품 UI에 표시하지 않는다.
- cancel과 예상된 입력 검증 실패를 앱 crash로 집계하지 않는다. 관측 SDK 도입 자체를 이번 작업 범위에 자동 포함하지 않는다.
- 모니터링·분석 SDK를 도입하면 수집 이벤트·삭제·보관·환경 분리·성능 비용·동의 필요 여부를 확인한다. debug 로그와 source map의 외부 업로드도 별도 범위다.
- 운영 장애는 재현 조건·영향 버전·확정 사실·가설을 구분하고, 국소 완화·복구·수정·회귀 검증을 기록한다. 관측하지 않은 원인을 단정하지 않는다.

## 성능·보안 변경의 검토 기준

최적화·보안 도구를 추가하기 전에 실제 문제와 적용 범위를 설명한다. 적용 후에는 정상 흐름뿐 아니라 실패 복구·접근성·플랫폼 호환·배터리/네트워크 비용이 나빠지지 않았는지 확인한다. 인증·계정·개인 데이터·실제 외부 환경을 바꾸는 작업은 해당 사용자 승인 범위를 따른다.
