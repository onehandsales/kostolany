# 테스트·코드 리뷰·전달 규칙

[규칙 진입점](README.md) · [공통 검증](../COMMON/QUALITY_AND_WORKFLOW.md) · [FE Goal 계획](../../../TODO/FE_GOALS.md)

## 작업 순서

1. 요청 범위, 기존 사용자 변경, 실행 환경, 적용 규칙과 실제 코드 상태를 확인한다.
2. 사용자 흐름·상태 수명·실패 범위와 필요한 원본 화면을 확인한다.
3. 구현과 중요한 행동·오류 사례의 테스트를 작성한다.
4. 타입·lint·관련 테스트를 실행하고 변경 코드를 리뷰한다.
5. 가능한 브라우저·플랫폼에서 실제 흐름을 실행하고 원본을 비교한다.
6. 발견한 결함을 수정하고 영향받은 검증을 다시 실행한다.
7. 구현, 검증 증거, 남은 차이·미검증을 보고한다. 다음 Goal은 자동 시작하지 않는다.

문서만 변경하면 링크·일관성·예시·변경 범위를 검증한다. 실행 코드에 영향이 없는 문서 변경 때문에 앱 테스트를 무조건 반복하거나 형식적인 테스트를 추가하지 않는다. 검증이 통과한 뒤 변경·실패·새 우려가 없으면 같은 검사를 계속 반복하지 않는다.

## 테스트의 책임

| 수준 | 확인할 것 | 이것만으로 증명하지 못하는 것 |
| --- | --- | --- |
| 순수 함수/상태 전이 | 정규화·검증·파생값·불변식·경계값 | 실제 UI 접근성·기기 레이아웃 |
| source/adapter | 요청 조건·응답 형식·오류·재시도 계약 | 실제 공급자·권한·네트워크 동작 |
| hook/컴포넌트 | 입력→선택/본문·로딩/실패·재시도·수명 | native 키보드·OS 제스처 |
| 화면 연결 | 실제 navigation·provider를 포함한 진입·복귀·공유 상태 | 설치·권한·process 재생성 |
| 브라우저 | PC 조작, 웹 렌더·콘솔, 모바일 폭 비교 | iOS·Android 실행 성공 |
| native E2E/수동 실행 | 터치·키보드·뒤로·스크린리더·생명주기 | 다른 OS/기기·실제 서버의 모든 조건 |
| 실제 연동 | 합의한 계정·네트워크·API·저장 결과 | fixture 결과만으로 대체 불가 |

커버리지 비율이나 스냅샷 수를 완료 기준으로 삼지 않는다. 사용자에게 중요한 실패가 발견되도록 검증한다. fixture 구현을 그대로 복사한 계산식으로 expected 값을 만들지 않는다.

## 사용자 행동 중심 테스트

- role·접근성 이름·보이는 문구로 조작한다. testID는 접근 가능한 의미로 식별하기 어려운 비의미적 요소 등 필요한 곳에만 쓴다.
- 실제 화면·navigation을 통째로 mock하지 않는다. 플랫폼 경계·시간·네트워크·저장소를 통제 가능한 대역으로 교체한다.
- UI 테스트와 순수 규칙 테스트를 구분한다. 내부 setState 호출 횟수보다 최종 선택·본문·수치·복귀 상태를 확인한다. 중복 요청 방지는 호출 횟수가 실제 요구이므로 검증할 수 있다.
- 응답 순서를 직접 제어할 수 있는 Promise를 사용해 오래된 성공·실패를 재현한다. 임의의 긴 sleep으로 타이밍 운에 의존하지 않는다.
- debounce·timeout에는 필요 시 fake timer를 쓰고 사용 중인 테스트 도구의 비동기 flush 계약을 지킨다. timer·spy·mock·store를 각 테스트 뒤 초기화한다.
- StrictMode, unmount, source 교체, 동일 query의 재진입, 사용자 범위 변경을 관련 기능에서 확인한다.
- 새 테스트 설명은 한글로 조건·행동·기대 결과가 드러나게 쓴다. 기존 테스트를 이름만 맞추려고 전부 고치지 않는다.

현재 RNTL은 14 계열이다. 설치된 `FE/node_modules/@testing-library/react-native/docs/guides/llm-guidelines.md`와 API를 확인한다. `render`·사용자 이벤트 등 비동기 API는 완료를 기다린다. 웹용 Testing Library 예제를 native에서 그대로 사용하거나 이전 major 버전의 동기 호출을 가정하지 않는다.

## 기능별 최소 검증 사례

해당 기능에 적용되는 행을 선택한다. 기능과 무관한 모든 테스트를 매번 추가하는 표가 아니다.

| 기능 | 최소 사례 |
| --- | --- |
| 조회 | 성공·빈 값·실패·재시도·동기 예외·잘못된 응답 identity·이탈 후 응답 |
| 검색 | 공백·정규화·일치/불일치·입력 변경·지우기·debounce·A→B→A·응답 역전 |
| 수준 전환 | 네 수준 선택과 본문·예시 일치, 공통 사실 유지, 늦은 성공/실패 |
| 좋아요·북마크 | 등록/해제·중복 입력·최종 의도·반응 수 중복/음수 방지·재시도·복구 |
| 쓰기 경합 | 오래된 실패가 새 성공 뒤 도착, 오래된 조회가 쓰기 성공 뒤 도착, 이탈·재진입 |
| 공유 상태 | 같은 ID의 홈·검색·상세 일치, 다른 ID/사용자 오염 없음, 화면 밖 항목 재표시 |
| 페이지 | 같은 cursor 중복 요청·페이지 경계·중복 ID·끝 페이지·정렬 변경 중 응답 |
| navigation | 선택 ID·진입 맥락, 앱 뒤로·native 이벤트 대역, 입력/목록/스크롤 복원 |
| 실제 인증 도입 시 | 취소·redirect 실패·세션 복원·동시 refresh·로그아웃·계정 전환·늦은 응답 격리 |
| 저장소 도입 시 | 초기 없음·읽기 실패·손상·버전 변경·migration·사용자별 삭제·재시작 |

예상 결과가 정책 선택에 따라 달라지면 테스트를 쓰기 전에 선택을 기록한다. 예를 들어 마지막 입력을 유지해야 하는 요구를 처리 중 버튼 비활성 테스트로 대체하지 않는다.

## 현재 검증 명령

Windows PowerShell, 저장소 루트 기준이다. 명령은 [package.json](../../../FE/package.json)의 실제 script를 우선한다. 도구 업데이트 후에는 지원 옵션을 다시 확인한다.

```powershell
Set-Location D:\git_repository\kostolany_project\FE
npm.cmd run typecheck
npm.cmd run lint
npm.cmd test
```

세 검사를 연속 실행하는 기존 명령은 `npm.cmd run check`다. 특정 Jest 설정은 `npm.cmd test -- --selectProjects iOS` 또는 `--selectProjects Android`로 확인한다. macOS에서는 `npm.cmd` 대신 `npm`을 사용한다. 작은 수정에서는 관련 테스트부터 실행하고 새 실패·공통 영향이 있으면 범위를 넓힌다. Goal의 완료 검사 범위는 FE Goal 공통 조건을 따른다.

```powershell
npm.cmd run export:android
npm.cmd run export:ios
```

`export:*`는 JS/Hermes 번들 검사다. APK·AAB·IPA 생성·설치·기기 실행의 증거가 아니다. 의존성 변경이 있을 때는 설치한 Expo SDK에 맞는 호환성 검사와 native 빌드 영향도 별도로 확인한다. 문서만 작성하면서 패키지 설치·ENV 교체·서버 재시작을 수행하지 않는다.

## 화면 비교와 플랫폼 검증 기록

| 기록 | 필요한 정보 |
| --- | --- |
| 대상 | flow/screen ID, 파일/원본 링크, 관찰한 범위 |
| 실행 | 날짜, 앱 코드/버전, 플랫폼·OS·기기 또는 브라우저, 빌드 모드 |
| 화면 조건 | viewport, 방향, 글자 크기, safe inset 확인 여부, 키보드·테마 |
| 경로 | 시작 상태, 입력·클릭, 기대 결과와 실제 결과 |
| 비교 | 배치·타이포·여백·이미지·상태별 차이, 자체 요소와 제외 기능 |
| 증거 | 실제 screenshot·로그·명령 결과의 위치, 이미지 보정 여부 |
| 한계 | 실행 못 한 기기·제스처·접근성·실제 연동 |

- 브라우저에서는 desktop과 작은 모바일 폭을 구분해 확인한다. 최소한 긴 한국어·이미지 없음·오류 문구·실제 클릭 흐름을 본다.
- native에서는 iOS와 Android 각각 작은 화면·큰 글자·Safe Area·키보드·뒤로 가기·복귀를 확인한다. 관련 기능은 VoiceOver/TalkBack도 실행한다.
- 원본을 보지 않았거나 구현을 캡처하지 않았다면 시각 비교 완료라고 하지 않는다. AI로 생성한 이미지나 DOM 값을 읽은 결과를 실제 렌더 캡처로 대체하지 않는다.
- 미검증 사유가 있어도 구현·자동 검증 등 독립적으로 가능한 작업을 마친다. 기기 검증 대기를 숨기거나 앱 전체 완료로 합치지 않는다.

## 코드 리뷰 관점

구현 설명을 읽은 뒤 코드와 테스트를 서로 대조한다. 독립 리뷰가 없으면 자기 검토였음을 구분하고, 실제로 수행하지 않은 제3자 리뷰를 기록하지 않는다.

| 관점 | 확인 질문 |
| --- | --- |
| 범위·보존 | 사용자 요청만 구현했는가, 기존 변경·미리보기·참고 파일이 보존됐는가 |
| 아키텍처 | 변경할 데이터의 소유자가 하나인가, 의존성 방향·수명이 명확한가 |
| 이름·주석 | 함수/메서드·컴포넌트·props 이름이 역할을 드러내는가, 설명 주석이 한글인가 |
| 타입·불변식 | 불가능한 상태·nullable·ID 혼동을 다루는가, 타입 억제가 문제를 숨기지 않는가 |
| 비동기 | 중복·응답 역전·cancel·실패·재시도·A→B→A·이탈을 다루는가 |
| 변경·복구 | 과거 실패/조회가 새 확정을 되돌리지 않는가, 숫자·공유 상태가 일치하는가 |
| 모바일 UX | 읽기·입력·뒤로·큰 글자·터치 영역·스크린리더·원본 비교에 누락이 없는가 |
| 자원·보안 | listener·timer 정리, 불필요한 전체 렌더, 민감 로그·저장·외부 연결은 없는가 |
| 테스트 | 코드의 버그를 실제로 잡을 기대값인가, 대역이 검증 대상을 지워버리지 않는가 |
| 전달 | 재현 경로·검증 명령·차이·미검증·외부 영향이 보고와 일치하는가 |

발견 사항은 영향과 재현 근거로 우선순위를 정한다. 데이터 오염·잘못된 선택·손실·권한·crash는 수정 후 검증한다. 이름·형식 개선은 기능 수정과 구분한다. 새 우려 없이 같은 전체 검사를 반복하는 대신 발견한 문제의 회귀 사례를 보강한다.

## native 빌드·출시 — 해당 작업 승인 시 적용

- Expo Go, development build, release build, 스토어 제출·심사를 구분한다. 새로운 native library나 native 설정 변경은 JS 업데이트만으로 반영된다고 가정하지 않는다. [Expo development build](https://docs.expo.dev/develop/development-builds/introduction/).
- 빌드 도구·지원 OS·target SDK·엔진·native 의존성·config plugin의 실제 조합을 기록한다. 생성된 native 프로젝트를 관리하는 방식과 수동 수정 보존 방법을 정한다. `prebuild --clean`을 기존 수정 확인 없이 실행하지 않는다.
- iOS는 Xcode·signing·entitlement·기기 설치, Android는 Gradle/JDK·manifest·서명·설치 조건을 확인한다. Windows에서 iOS JS 번들을 만들었다고 iOS 앱 빌드를 완료했다고 하지 않는다.
- 개발·검증·운영 환경의 application ID·bundle ID·API 주소·인증 callback·서명·권한을 구분한다. 비밀 값과 서명 파일을 저장소에 포함하지 않는다.
- OTA를 도입할 경우 update와 native runtime의 호환성을 관리한다. native module·설정이 달라지면 호환 runtime과 새 binary 필요 여부를 확인한다. rollout·중단·복구 기준 없이 일괄 업데이트하지 않는다. [Expo runtime version](https://docs.expo.dev/eas-update/runtime-versions/).
- 이전 앱 버전은 계속 존재한다. API·저장값·schema 변경의 하위 호환과 migration 실패·rollback 이후 읽기를 검토한다. 출시된 DB/API를 모바일 UI 일정에 맞춰 임의 변경하지 않는다.
- crash·접근성·권한·offline·업데이트 설치·기존 데이터 복원 확인 후 출시 상태를 판단한다. 개인정보 고지·SDK 수집·스토어 정책은 출시 시점의 공식 요구를 따로 확인한다.
- 실제 인증서·계정·외부 업로드·배포는 요청된 승인 범위 안에서 수행한다. 로컬 코드 검증과 배포 권한을 같은 것으로 간주하지 않는다.

## 완료 보고의 형식

결과 문서는 필요에 맞게 작성하되 아래 정보가 빠지지 않아야 한다.

```text
구현: 변경한 사용자 행동과 범위
설계: 상태 소유자·수명·동시성 처리·화면용 기본안
검증: 실제 명령, 테스트 결과, 브라우저/각 플랫폼 실행 결과
화면: 원본 ID와 비교 결과, 남은 차이
미검증: 실행하지 못한 항목과 이유
보존·외부 영향: 기존 변경, 참고 파일, 의존성·ENV·외부 서비스 변경 여부
남은 범위: 후속 기능과 실제 연동·기기 확인 필요 사항
```

`통과`, `실패`, `미실행/미검증`, `해당 없음`을 구분한다. 구현·자동 검증만 끝났다면 “구현 완료 / 실제 기기 검증 대기”처럼 기록한다. Goal 번호가 진행됐다는 이유로 이전 Goal의 미검증을 완료로 바꾸지 않는다. 커밋·push·배포의 실제 수행 여부와 해시는 해당 작업에서 확인한다.
