# API 계약 규칙

기준일: 2026-11-20. [공통 적용 기준](ENGINEERING_RULES.md)을 따른다. API 명세 작성과 실행 API 구현·배포는 별도 상태다.

## API-SPEC-001 — 화면 행동에서 구현 계약까지

**대상:** 신규 API, 응답·권한·상태 전이·정렬 등 공개 동작을 바꾸는 작업.

실제 모바일·서버 연결 전에 해당 사용자 흐름의 요청·응답·오류 계약을 작성한다. 화면 mock과 계약 초안은 병행할 수 있다. 전체 서비스 명세를 다 작성해야 첫 기능을 시작할 수 있는 것은 아니다.

계약의 기본 위치는 이 폴더 하위 `API_SPEC/<기능명>.md`로 제안한다. 아직 이 경로에 endpoint 명세나 실행 API는 없다. OpenAPI를 도입하면 생성 명세와 사람이 읽는 정책 설명의 역할을 나누고 필드 정의를 중복 관리하지 않는다.

### 기능별 명세의 필수 항목

| 항목 | 기록할 내용 |
| --- | --- |
| 상태 | 초안 / 구현 기준 확정 / 구현됨 / 배포 검증됨 |
| 목적·소비자 | 화면의 어떤 행동을 처리하는지, iOS·Android 소비 여부 |
| 요청 | method·path·query·body·인증·검증 조건 |
| 응답 | HTTP 상태, JSON 예시, 필드 타입·의미·nullable·생략 여부 |
| 오류 | 안정적인 error code, HTTP 상태, 사용자에게 보여줄 의미 |
| 목록 | 정렬 키·방향·동률 처리·페이지 경계·다음 페이지 조건 |
| 권한 | 읽기 공개 범위, 현재 사용자, 데이터 소유권 |
| 쓰기 | 변경 데이터, 트랜잭션과 롤백 범위, 중복·동시 요청 처리 |
| 외부 연동 | 타임아웃·재시도·부분 실패·후속 작업 |
| 관측 | requestId, 필요한 업무 식별자, 민감정보 제외 |
| 호환성 | 기존 앱 버전 영향과 변경·폐기 방법 |

필드 정의는 `이름 / 타입·형식 / 필수 여부 / nullable / 생략 조건 / 의미 / 허용 값·범위·길이 / 예시`를 모두 작성한다. 숫자에는 단위, 시각에는 사건의 의미·시간대, ID에는 식별 대상과 클라이언트 취급 방식을 적는다. 기본값을 적용하는 조건과 입력을 거절하는 조건을 구별한다.

권한은 `행위자 / 대상 / 공개 범위 / 소유권 / 허용 작업 / 거절 결과`로 작성한다. 상태 전이는 `현재 상태 / 요청 행동 / 선행 조건 / 다음 상태 / 함께 변경할 데이터 / 충돌 결과`로 작성한다. 해당 없는 항목은 이유와 함께 해당 없음으로 표시한다.

각 기능에 정상 JSON과 중요한 실패 JSON, 빈 목록·마지막 페이지·선택 값 누락 사례를 포함한다. 부분 갱신은 필드 생략·명시적 null·빈 문자열·빈 배열의 의미와 갱신 가능한 필드를 정한다.

구현 기준 확정은 계약을 구현 가능한 수준으로 정리했다는 뜻이다. 이미 권한을 받은 구현 작업에서 별도의 형식적 승인 단계를 추가하지 않는다. 제품 정책이 달라지거나 의미가 불명확할 때만 필요한 결정을 요청한다.

**금지·예외:** Medium 공식 도움말과 관찰한 UX는 동작의 참고 자료다. 화면이나 공개 API 문서를 내부 DB·서버 API의 증거로 취급하지 않는다. 우리 서비스의 미정 권한·수익화·추천 정책을 원본 서비스와 자동으로 동일하게 확정하지 않는다.

**검증·완료:** 화면 행동 → 유스케이스 → endpoint → 권한·데이터 소유자 → 성공/실패 테스트의 연결을 명세에 남긴다. JSON 예시가 필드 표와 일치하고, 구현에 필요한 미정 항목은 해당 기능 착수 전에 해소한다. 다른 기능의 미정 정책까지 모두 결정해야 한다는 의미는 아니다.

## API-SEC-001 — 입력·인증·오류의 공개 계약

**대상:** API 경계의 입력 검증, 사용자 신원, 오류 응답.

- JSON 필드는 `camelCase`, 시각은 의미를 명시한 ISO 8601 형식으로 주고받는다.
- 사용자 신원은 검증된 access token에서 얻는다. 요청 body의 `userId`를 권한 근거로 신뢰하지 않는다.
- `401`은 인증 문제, `403`은 인증 후 권한 부족으로 구분한다. 존재 여부를 숨겨야 하는 자원은 `404` 처리 여부를 계약에 적는다.
- 원시 DB·AI 공급자 오류나 stack trace를 사용자 응답에 노출하지 않는다.
- 오류 JSON은 `code`, `message`, `requestId`를 기본안으로 삼고 첫 계약에서 형태를 확정한다.
- 오류 코드는 기계가 분기할 안정적인 식별자이며 문구 변경과 분리한다. 필드별 오류가 필요하면 필드 경로·코드·안전한 설명 구조를 정의한다. 입력 원문·토큰·SQL·스택을 반환하지 않는다.
- 본문 크기·문자열 길이·목록 크기·업로드 크기·검색 길이·페이지 크기의 제한은 해당 계약에 숫자로 적는다. 미정 한도를 임의의 무제한으로 구현하지 않는다.
- 권한 판단용 사용자 ID는 검증된 신원에서 얻는다. 대상 사용자·작성자 ID를 받는 API는 신원과 구별하고 그 대상을 지정할 권한을 추가 검사한다.
- 글·댓글 등 rich text를 받으면 허용하는 문서 구조·태그·속성·URL scheme과 정제 책임을 정의한다. 원문 HTML·스크립트를 신뢰해 실행하거나 임의의 외부 URL을 서버가 가져오게 하지 않는다. 저장 검증과 소비자의 안전한 렌더링 책임을 구분한다.
- 공개 검색·반응·생성 요청 등 남용 가능한 동작은 인증 여부와 별도로 호출량·동시 요청 제한, 제한 대상 키, 제한 초과 응답·재시도 가능 시점을 정한다.

**검증·완료:** 잘못된 입력, 인증 누락·오류, 다른 사용자의 자원, 허용하지 않은 필드, 존재 여부 은닉 정책을 API 테스트로 확인한다. 거절 응답은 계약의 상태·코드를 유지하고 데이터 변경을 유발하지 않는다. 공개 읽기의 예외는 endpoint별로 명시한다.

## API-WRITE-001 — 재시도와 동시 쓰기의 의미

**대상:** 등록·수정·발행·삭제·작업 요청.

- 좋아요·북마크는 등록/해제를 구분하는 멱등적 요청을 우선 검토한다. 재시도 때 상태가 뒤집히는 단순 toggle은 피한다.
- 동일 요청의 첫 실행·재실행·처리 중 중복·처리 완료 후 중복에 대한 응답을 정의한다. 멱등성은 효과의 반복 안전성이며 모든 응답 본문이 반드시 동일하다는 뜻은 아니다.
- 동시 편집에는 기대 버전의 전달 위치와 충돌 시 응답·재조회 방법을 정한다. 오래된 요청을 무조건 최종 작성으로 덮어쓰지 않는다.
- 비동기 API는 작업 식별자, 상태 조회, 실패·재시도·취소의 의미와 결과 보관 기간을 정의한다. 접수 성공을 작업 완료 응답으로 표현하지 않는다.
- 삭제는 물리 삭제·공개 중단·논리 삭제 중 선택한 의미, 반복 삭제 결과, 연관 데이터 처리와 복구 여부를 적는다.

**금지·예외:** 조회 후 없으면 저장하는 코드만으로 중복 방지를 선언하지 않는다. idempotency key의 적용·재사용·만료는 [트랜잭션 규칙](../BACKEND_AGENT/TRANSACTION.md)을 따른다. 실제 반복 횟수를 세는 기능은 절대 상태 등록과 다르므로 별도 계약을 사용한다.

**검증·완료:** 연속·동시 중복, 응답 유실 후 재시도, 오래된 수정 버전, 다른 사용자와 같은 키 사용을 적용 가능한 명령에 검증한다. 최종 데이터와 응답이 계약에 일치해야 한다.

## API-LIST-001 — 정렬·페이지·공개 범위

**대상:** 피드·검색·사용자 목록·작성자 글·북마크 등 목록 API.

- 최신순·인기순·추천순은 각각 계산 기준을 정의한다. 페이지네이션은 정렬과 함께 설계하고 커서를 쓰면 동률·점수 변동을 고려한다.
- 미게시·생성 실패 콘텐츠가 공개 조회에 섞이지 않도록 게시 조건을 조회 계약에 포함한다.
- 정렬 키별 방향·null 위치·동률 처리, 기본/최대 페이지 크기, 다음 페이지 판정과 빈 결과 구조를 작성한다. 사용자와 확정한 정렬에 임의의 추가 키를 넣지 않는다.
- 커서는 정렬·필터·사용자 범위·필요한 버전 정보를 일관되게 적용하고 변조·잘못된 값·만료 처리 계약을 가진다. 커서에 넣은 사용자 ID를 인증 근거로 신뢰하지 않는다.
- 데이터·인기 점수가 페이지 사이에 바뀔 때 snapshot 고정 또는 변경 허용 정책을 정한다. 고정하지 않는 목록에 대해 무조건 중복·누락 없음이라고 보장하지 않는다.
- 선택한 설명 수준이 준비되지 않았을 때의 제외·오류·명시적 대체 여부를 정한다. 다른 수준으로 조용히 바꾸지 않는다.

**검증·완료:** 같은 정렬 값·null·빈 목록·최대 크기·마지막 페이지·페이지 사이 삽입/삭제/점수 변경·잘못된 커서를 검증한다. 권한·공개 조건이 모든 페이지와 count 계산에 동일하게 적용되어야 한다.

## API-COMPAT-001 — 모바일 버전 호환과 계약 변경

**대상:** 필드·타입·enum·상태 코드·정렬·오류·기본값 변경.

- 모바일 앱은 즉시 전원 업데이트되지 않는다. 기존 클라이언트와 호환되는 변경을 우선하고, breaking change는 버전·전환 절차를 정한다.
- 응답 필드 추가도 strict decoder, enum 추가도 기존 앱의 분기 처리에 영향을 줄 수 있으므로 소비자 검증을 수행한다.
- 호환되지 않는 변경은 병행 제공 범위, 데이터 변환, 지원 종료 조건, 실패 시 복구를 기록한다. 버전 URL 추가만으로 기존 데이터와 소비자 전환이 완료됐다고 하지 않는다.
- OpenAPI를 사용하면 기계적인 필드·타입·필수 값과 실제 응답을 검사한다. 정책·권한·전이의 설명은 기능 명세에 두고 동일 정의를 수동으로 이중 관리하지 않는다.

**검증·완료:** 변경 전 지원 대상 클라이언트의 요청·응답 fixture와 새 계약 테스트를 통과해야 한다. 실행 API가 없으면 상태는 명세/초안이며 구현·배포 검증 상태로 승격하지 않는다. 예외는 공통 기록 절차를 따른다.

## 기능 계약을 나누는 기준

1. 콘텐츠 목록·상세와 설명 수준 선택.
2. 로그인 이후 내 프로필 확인·필요 시 멱등적 초기화.
3. 좋아요 등록·해제, 북마크 등록·해제·목록.
4. 조회 이벤트와 조회수 노출.
5. 최신·인기·추천 정렬 정책.

이 목록은 초기 콘텐츠 흐름의 출발점이며 전체 범위나 고정 구현 순서가 아니다. 완료된 Medium UX/UI의 글쓰기·작성자·댓글·팔로우·목록·설정 등은 각 흐름의 서버 책임과 초기 활성 범위를 정의한 뒤 계약에 포함한다. 화면 복제는 결제 실행·외부 작가 모집의 정책 확정을 뜻하지 않는다. 실제 endpoint 경로·필드·DDL은 해당 계약에서 정한다.
