# Backend·DB 공통 규칙의 적용 기준

기준일: 2026-11-20. 이 문서는 Backend·DB 규칙과 API 계약·검증 문서를 읽는 기준이다. 규칙 작성은 실행 코드, 검사 도구, DB 설정 또는 배포의 구현 완료를 뜻하지 않는다.

## ENG-RULE-001 — 적용 범위와 우선순위

**대상:** `BACKEND_AGENT`, `DB_AGENT`, 이 폴더의 계약·검증 문서 및 이후 작성하는 서버·DB 코드.

1. 최신 사용자 지시, 확정된 기능 계약, 이 문서와 영역별 상세 규칙 순서로 해석한다. 기능 계약은 품질 규칙의 예외를 암묵적으로 만들 수 없다.
2. 규칙의 `필수`, `금지`, `완료 조건`은 구현·리뷰 기준이다. `기본안`은 선택의 출발점이고, `예시`는 실제 스키마·정책·명령의 확정이 아니다.
3. 이 개정은 FRONT_AGENT의 작성된 규칙과 진행 중인 FE 작업을 변경하지 않는다. 공유 API 의미가 달라지면 계약에서 조율한다.
4. 초기 제품 범위 문서에는 이전 MVP의 제외 기능이 남아 있다. 최신 방향은 Medium UX/UI와 사용자 흐름을 참고한 기능 기반을 만들고 서비스에 맞게 구체화하는 것이다. 과거의 댓글·팔로우·글쓰기 제외 문구를 최신 기능의 일괄 금지로 사용하지 않는다.
5. 사업 목표는 사용자 확대이고, 콘텐츠 목적은 국내외 뉴스를 코스톨라니 관점에서 읽으며 독자의 투자 판단 기준을 기르는 것이다. 초기 발행자는 운영자 한 명이며 향후 다른 작가가 참여할 수 있게 한다. 다중 작가 모집·유료화는 필수 전제가 아니다.
6. 초등·중등·고등·성인용 콘텐츠는 같은 사실을 공유하되 표현과 예시를 달리한다. 실제 나이 수집·인증, 부분 발행 허용, 사람의 검수 필수 여부, 작가 모집·권한 부여 절차는 별도 정책이다.

**금지:** 옛 MVP를 근거로 최신 범위를 축소하거나, 화면·예시·기본안을 근거로 사업 정책과 외부 연결을 확정한 것으로 기록하지 않는다.

**검증·완료:** 변경 문서에서 확정 방향·구현 선택·미정 정책·실제 결과를 구별하고, 사용자 흐름과 충돌하는 옛 규칙은 적용 범위 안에서 정리한다. 범위 밖 충돌은 위치와 영향을 기록한다.

## ENG-RULE-002 — 규칙 형식과 예외 기록

**대상:** 이 문서와 링크된 영역별 규칙의 추가·수정.

각 규칙은 고유 ID가 있는 절로 관리한다. 다음 항목은 해당 절의 본문·표·검증 문단에 구체적으로 작성한다.

별도 `기본안`·`예시` 표시가 없는 실행 지침은 필수다. 개별 규칙에 별도 예외가 없으면 이 절의 공통 예외 절차를 적용하며, 예외 기록 없이 생략할 수 없다. 금지 사항은 `금지` 표기와 `하지 않는다` 등 명시적인 제한 문장을 포함한다.

| 항목 | 작성 기준 |
| --- | --- |
| 식별자 | `BE-TX-001` 등 변경 후에도 유지할 ID; 삭제한 ID를 다른 뜻으로 재사용하지 않음 |
| 적용 대상 | 적용되는 계층·파일·입력·변경 상황 |
| 필수 동작 | 작성 위치, 처리 순서, 보장할 불변식, 산출물 |
| 금지 사항 | 허용하지 않는 의존·데이터 변경·실패 처리 |
| 예외 조건 | 명시된 예외 또는 아래 공통 절차; 예외가 없으면 임의 생략 불가 |
| 검증 방법 | 입력·실행 방법·관찰할 결과와 증거 |
| 완료 조건 | 누락 0건, 상태 불변, 중복 1건 등 판단 가능한 결과 |

예외는 해당 변경의 설계 기록에 `규칙 ID / 이유 / 대상 파일·기능 / 위험 / 대체 검증 / 책임자 / 해소 시점 또는 재검토 조건`을 남긴다. 상시 설계 선택이면 임시 예외로 방치하지 않고 근거와 함께 규칙을 개정한다. 단순 일정 부족이나 도구 미설치는 통과의 근거가 아니다.

이미 승인된 범위의 가역적 구현 선택에 별도 승인 절차를 추가하지 않는다. 사용자 필수 조건인 한글 주석과 의미 있는 테스트를 작성자 판단으로 면제하지 않는다. 제품 의미를 바꾸거나 파괴적 변경으로 범위를 넓혀야 할 때만 필요한 결정을 요청한다.

**검증·완료:** ID 중복, 서로 다른 문서의 모순, 실행 불가능한 완료 조건을 점검한다. 모든 예외에 대체 검증과 재검토 조건이 있고, 실제 실행하지 않은 검증을 성공으로 표시하지 않는다.

## ENG-DESIGN-001 — 설계 결정과 변경 영향

**대상:** 모듈 경계, 외부 공급자, 데이터 소유권, 공개 계약, 정합성·성능 전략을 바꾸는 작업.

변경 설명에 `문제 / 현재 제약 / 검토한 대안 / 선택 이유 / 포기한 이점 / 변경 대상 / 검증 / 복구 또는 전환 방법`을 남긴다. 작은 변경은 해당 계약이나 변경 설명에 기록하고, 장기적으로 재참조할 결정만 별도 결정 문서로 분리한다.

| 변화 | 반드시 설명할 영향 |
| --- | --- |
| 작가 추가 | 기존 글의 작성자 관계, 발행 권한, 소유권 검사와 기존 독자 데이터 |
| 설명 수준 추가 | 생성 입력·출력, 저장 제약, API 값, 기존 앱의 알 수 없는 값 처리 |
| AI·RSS 공급자 변경 | 어댑터 교체 범위, 오류·사용량 변환, 결과 계약과 회귀 샘플 |
| 서버·worker 증설 | 작업 소유권, 중복 실행, 연결 풀 합계, 동시성 검증 |
| 캐시·집계 도입 | 원본 데이터, 만료·무효화, 허용 지연, 재계산과 권한 분리 |

**금지:** 사용 사례가 없는 범용 프레임워크, 모든 서비스의 기계적 인터페이스화, 근거 없는 분산 시스템 도입. 성능 개선은 측정 대상과 전후 결과를 기록한다.

**검증·완료:** 변경 시나리오별로 수정할 경계와 유지할 계약을 설명하고 테스트에 연결한다. 확장 가능한 저장 구조만으로 API·앱까지 자동 호환된다고 주장하지 않는다.
