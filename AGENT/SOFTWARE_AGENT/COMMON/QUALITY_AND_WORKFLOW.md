# 검증과 작업 규칙

기준일: 2026-11-20. [공통 규칙](ENGINEERING_RULES.md)의 필수·예외·상태 구분을 따른다. 아래 검증 task는 Backend 초기화 때 구현해야 할 계약이며 현재 실행 도구가 설치됐다는 의미가 아니다.

## QLT-WORK-001 — 범위 확인과 변경 추적

**대상:** 문서·서버·DB의 모든 변경.

1. 현재 제품 범위·구현 상태·변경 파일을 확인한다.
2. 이번에 완성할 사용자 흐름을 정한다.
3. 필요한 API·DB·실패 처리 계약을 정리한다.
4. 최소 범위로 구현하고 중요한 동작을 검증한다.
5. 변경 내용, 실행한 검증, 미검증 외부 연동, 남은 문제를 기록한다.

문서·mock·코드·로컬 검증·실제 공급자 연동·배포는 다른 상태다. 커밋은 명시적 요청이 있을 때만 수행한다. 기존 ENV·DB·서버를 문서 작업을 위해 변경하지 않는다.

다른 터미널이 작업 중이면 시작 시 Git 변경과 대상 파일을 확인하고, 편집 직전에 대상이 바뀌었는지 재확인한다. 다른 작업의 변경을 정리·되돌리거나 공용 상태 문서를 통째로 덮어쓰지 않는다. 공유 파일을 수정해야 한다면 자신의 변경 부분만 반영한다.

**검증·완료:** 최종 diff가 승인된 경로·기능에 한정되는지 확인한다. 결과에는 변경 이유, 변경 파일, 실제 실행한 검증, 남은 한계와 후속 작업을 적는다. 기존 테스트 결과·과거 커밋의 통과를 현재 변경의 증거로 재사용하지 않는다.

## QLT-TEST-001 — 동작 변경에 필요한 테스트

**대상:** 새 업무 로직, API·권한·상태·DB·외부 연동 동작 변경과 버그 수정.

Backend는 JUnit Jupiter를 기본으로, 필요한 협력 객체에 MockK를 사용한다. DB 특성은 격리 PostgreSQL과 Testcontainers로 검증하는 것을 기본안으로 한다. 정확한 라이브러리 버전과 실행 명령은 프로젝트 초기화 때 고정한다.

도구 근거: [Testcontainers PostgreSQL 모듈](https://java.testcontainers.org/modules/databases/postgres/). 테스트 범위와 완료 조건은 아래 프로젝트 규칙으로 정한다.

| 대상 | 반드시 설명할 수 있어야 하는 검증 |
| --- | --- |
| 순수 정책 | 게시 가능 조건, 단계별 콘텐츠 구성, 정렬 계산 경계 |
| 인증·권한 | 누락·만료·잘못된 토큰, issuer/audience 오류, 다른 사용자 북마크 접근 차단 |
| DB 원자성 | 여러 쓰기 중 실패할 때 전체 롤백, 실제 서비스 프록시 경유 호출 |
| 중복·동시성 | 중복 좋아요·북마크·기사 처리, 동시 요청 때 제약과 결과 |
| 외부 공급자 | timeout·429·5xx·잘못된 JSON·일부 단계 누락·재처리 |
| API | 요청 검증, 응답 타입·null·오류·페이지 순서 |
| 모바일 | 로그인 복귀, 세션 복원, 북마크 실패 복구, 수준 변경, 빈 목록·네트워크 오류 |
| 통합 흐름 | 수집 → 생성 → 게시 → 모바일 읽기, 로그인 → 반응 저장·재조회 |

업무 동작을 추가하거나 수정할 때 같은 변경에 의미 있는 테스트 코드를 포함한다. 각 테스트는 `준비 조건 / 실행 / 예상 응답 / 예상 저장 상태·부수 효과`를 드러낸다. 적용 가능한 정상·거절·경계·실패 사례를 작성하고, 해당하지 않는 위험은 이유를 기록한다. 기능 계약의 시나리오와 테스트 파일·테스트 이름을 연결한다.

| 변경 | 최소 확인할 구체적인 결과 |
| --- | --- |
| 권한·소유권 | 허용 사용자 성공, 다른 사용자 거절, 거절 후 데이터·작업 예약 불변 |
| 여러 저장의 원자성 | 앞선 저장 후 뒤쪽 실패·commit 제약 실패 시 전체 롤백 |
| 중복 등록 | 순차·동시 요청 후 관계 1개; 집계를 저장하면 실제 변경 횟수만 반영 |
| 수정 버전 | 오래된 버전 요청 거절, 최신 데이터 보존 |
| 외부 실패 | timeout·429·5xx·잘못된 JSON의 오류 분류·제한된 재시도·종료 상태 |
| 재생성·발행 | 실패 시 기존 공개 버전 보존, 늦은 결과의 최신 편집 덮어쓰기 차단 |
| 정렬·페이지 | 동률·null·마지막 페이지·데이터 변동에서 합의한 순서와 경계 |
| 회귀 수정 | 수정 전 결함을 재현하는 테스트와 수정 후 기대 결과 |
| DB 변경 | 신규 설치·이전 버전 업그레이드·제약·주석·인덱스·기존 데이터 보존 |

- 핵심 제약·동시성·롤백을 repository mock만으로 검증했다고 하지 않는다.
- PostgreSQL 특성을 확인해야 하는 테스트를 H2 결과로 대체하지 않는다.
- 테스트용 외부 AI·RSS는 fixture나 stub을 사용한다. 실제 외부 호출 검증은 구분하고 비용·데이터 영향을 통제한다.
- 테스트는 구현 줄 수보다 실패 시 손실·오류 가능성을 기준으로 작성한다. 단순 getter·문서 수정에 형식적 테스트를 추가하지 않는다.
- 전체 커버리지 100%를 목표로 강제하지 않는다. 핵심 실패 사례가 검증되는지 본다.
- 테스트 메서드 전체의 자동 롤백만 믿지 않는다. 필요한 경우 실제 서비스 커밋·롤백과 다른 트랜잭션에서의 관측을 확인한다.
- iOS·Android 둘 다 대상이다. 한 플랫폼 성공을 양쪽 성공으로 기록하지 않는다.

**예외:** 문서·주석만의 수정과 자동 생성 getter에 동작을 복제하는 형식적 테스트를 만들지 않는다. 다만 주석 검사기·마이그레이션 주석 검사는 각 규칙의 자동 검증 대상이다. 의미 있는 테스트 필수 조건을 일정이나 커버리지 수치로 대체하지 않는다.

**검증·완료:** 테스트가 검증할 동작을 제거하거나 잘못 바꾸면 실패하는지 리뷰한다. 테스트 수·커버리지 100%만으로 완료 판정하지 않는다. 관련 시나리오가 모두 통과하고 skip·미실행은 별도로 보고한다.

## QLT-TEST-002 — 테스트 격리와 재현성

**대상:** 단위·API·DB·동시성·외부 어댑터 테스트 및 테스트 도구 코드.

- 테스트 코드에도 [BE-DOC-001](../BACKEND_AGENT/KOTLIN_SPRING.md)의 한글 주석을 적용한다. 준비 데이터는 해당 사례에 필요한 최소 조건만 만들고 fixture가 검증할 규칙을 우회하지 않게 한다.
- DB 테스트는 운영과 호환되는 고정 PostgreSQL 버전과 필요한 확장으로 실행한다. Testcontainers 또는 동등한 격리 환경을 사용하고 공유·운영 DB URL이면 실행을 차단한다.
- 마이그레이션 테스트는 실제 SQL을 적용한다. Hibernate 자동 생성 스키마로 Flyway 검증을 대신하지 않는다. Supabase 전용 객체는 별도 fixture 또는 격리 Supabase 검증으로 구분하며 일반 PostgreSQL 통과를 플랫폼 전체 성공으로 기록하지 않는다.
- 시간은 제어 가능한 Clock, 난수는 재현 가능한 입력으로 다룬다. 실행 순서·개발자 로컬 데이터·실제 AI 응답에 의존하지 않는다.
- 병렬 테스트는 DB/schema·데이터 키·포트·파일을 격리한다. 동시성 검증은 여러 연결을 실제 겹치게 실행하고 barrier/latch와 bounded timeout으로 순서를 제어한다. worker의 예외를 수집하고 종료를 기다린 뒤 최종 상태를 확인한다.
- HTTP 어댑터는 요청·응답 stub으로 timeout·오류·파싱·재시도를 검증한다. 실제 공급자 검증은 별도 실행군으로 두고 데이터·비용 범위 안에서 수행한다.
- 불안정 테스트를 통과할 때까지 반복 실행하여 정상으로 보고하지 않는다. 원인과 재현 조건을 기록하고 수정한다. 격리하거나 skip하면 해당 검증은 미완료다.

**검증·완료:** 개별 실행과 관련 묶음 실행에서 같은 결과가 나와야 한다. 필요한 DB 환경 부재는 명시적인 검증 실패/미실행이며, 자동 skip 후 전체 통과로 표현하지 않는다. 외부 연결·배포 증거는 로컬 stub 결과와 분리한다.

## QLT-GATE-001 — 초기화 때 연결할 자동 검사와 완료 조건

**대상:** Backend 빌드·CI 초기화 및 이후 코드·DB 변경.

다음 이름은 초기화 때 제공할 Gradle task 계약이다. 현재 task가 존재하거나 이번 문서 작업에서 실행됐다는 뜻이 아니다. 도구 고유 task 이름이 다르면 아래 이름의 aggregate task로 연결하거나 실제 이름과 동등 범위를 실행 문서에 명시한다.

| Task 계약 | 실행 범위 | 실패 조건 |
| --- | --- | --- |
| `formatCheck` | 선택한 Kotlin 포맷 검사·정적 검사 | 포맷 위반, 승인되지 않은 정적 규칙 위반 |
| `koreanDocCheck` | 운영·테스트·보조 코드 선언의 한글 주석 | 누락·공백·한글 설명 없음·잘못된 첫 줄 형식 |
| `architectureTest` | 모듈·계층·공개 타입 의존 | 순환·금지 계층·다른 모듈 내부 참조 |
| `test` | 순수 정책·서비스·API 계약 등 빠른 검증 | 관련 정상·실패 시나리오 불일치 |
| `integrationTest` | 실제 Spring·격리 PostgreSQL·어댑터 통합 | 권한·트랜잭션·동시성·계약 불일치 |
| `migrationTest` | 빈 DB 및 지원하는 이전 DB 버전에서 migration | 적용·데이터 보존·제약·인덱스 검증 실패 |
| `schemaCommentTest` | 적용 후 앱 소유 테이블·전체 컬럼 주석 | 검사 대상 누락 또는 한글 한 줄 설명 누락 |
| `check` | 컴파일과 위 필수 검사 집계 | 필수 검사 실패·누락; DB 검사 silent skip 금지 |

초기화 산출물에 task별 명령, 작업 디렉터리, 필요한 환경, 테스트 대상, 결과 위치를 적는다. 예를 들어 Windows의 `./gradlew.bat check`는 Wrapper와 task를 실제 구현한 이후 실행하는 명령이다. secret을 명령 예시에 넣지 않는다.

**금지·예외:** 검사기가 아직 없으면 수동 리뷰 결과와 자동화 미구현을 따로 기록한다. 자동화가 없는 상태를 초기화 완료로 판단하지 않는다. 동등한 격리 PostgreSQL과 대체 검사 도구는 범위·재현 명령·통과 기준을 기록하면 사용할 수 있다.

**검증·완료:** 의도적으로 만든 작은 위반 fixture가 주석·구조·DB 주석 검사를 각각 실패시키는지 검증한다. 첫 초기화에서는 깨끗한 환경의 전체 `check` 성공을 확인한다. 이후 작업 중에는 관련 검사로 반복을 줄이고 완료 판단에 필요한 전체 검증을 수행한 뒤 변경·실패·새 우려가 없으면 반복하지 않는다.

## QLT-OPS-001 — 관측·성능·실패 복구

**대상:** API·DB·RSS·생성 작업·파일 처리의 운영 동작.

- 구조화 로그에 requestId, operation, 필요한 내부 userId·articleId·jobId, 소요 시간, 결과를 남긴다.
- access/refresh token, DB 비밀번호, 비밀 키, 개인 프로필 원문을 로그에 남기지 않는다.
- RSS 수집 결과, 생성 성공·실패·재시도, AI 사용량·비용, API 오류·지연, DB 연결 풀 상태를 확인할 수 있게 한다.
- 로그에는 재처리에 필요한 식별자를 남기고, 상세 생성 입력은 접근과 보관 정책을 가진 저장소에서 관리한다.
- 성능 개선은 실제 쿼리·실행 계획·응답 지연 등 근거를 남긴다. 부하 테스트 결과와 실제 사용자 트래픽을 구분한다.
- 수집 스케줄러와 API를 같은 서버에 두는 초기안은 가능하다. 생성 작업이 API 응답과 DB 연결을 오래 점유하지 않게 한다.
- 외부 requestId는 길이·문자 제한을 검증하거나 내부 식별자를 새로 만든다. 로그 주입을 허용하지 않는다. 비밀번호·토큰·서명 URL·전체 프롬프트·사용자 원문을 구조화 필드에 넣지 않는다.
- 로그는 실패 원인과 재처리 대상을 추적할 수 있게 하고, metric label에는 사용자·기사·작업 ID처럼 무한히 증가하는 값을 사용하지 않는다.
- 주요 API의 p95 지연·오류율, 연결 풀 사용량·대기, 작업 대기 시간·재시도·최종 실패, AI 사용량·비용을 측정한다. 경보 기준은 실제 환경·허용 지연·예산을 숫자로 정하고 대응 행동과 연결한다.
- 성능 검증에는 데이터 수·분포·페이지 크기·동시 요청 수·실행 환경·지연·쿼리 수·실행 계획을 기록한다. 모든 작은 테이블의 순차 스캔을 인덱스 결함으로 단정하지 않는다.
- 장애 절차에는 생성 일시 중단, 실패 작업 조회·제한된 재처리, 자격 증명 교체, 잘못된 공개 버전 복구, DB forward fix 또는 복원 절차의 책임자를 정한다.

**검증·완료:** 실패를 주입했을 때 오류 응답의 식별자로 로그와 작업을 찾을 수 있고 민감정보가 없어야 한다. timeout·한도 도달·연결 실패 시 정의된 상태와 복구 경로를 확인한다. 수치·백업·복구는 실제 확인한 환경과 일자를 기록한다.

## QLT-DONE-001 — 변경별 검증과 완료 보고

**대상:** 작업 종료, 리뷰, 배포 준비 결과.

| 변경 | 확인 범위 |
| --- | --- |
| 문서 | 상대 링크, 모순, 미정·구현 상태, 비밀 값 포함 여부 |
| Backend | 컴파일·포맷/정적 검사·관련 테스트, 필요 시 빌드 |
| DB | migration 적용, 제약·인덱스·rollback/forward fix 영향, 격리 DB 검증 |
| 모바일 | 타입 검사·lint·관련 테스트, 영향받는 플랫폼 실행·빌드 |
| 배포 | 설정·마이그레이션 순서·health·핵심 API·복구 절차 |

실제 스크립트가 생기기 전 검증 명령을 실행 완료로 기록하지 않는다. 검증이 통과한 뒤 변경이나 새로운 우려가 없으면 불필요하게 반복하지 않는다.

배포 작업이 승인된 경우에는 호환 스키마 확장 → 서버 배포·health/핵심 API 확인 → backfill 검증 → 구버전 사용 종료 확인 → 파괴적 정리 순서를 변경에 맞게 구체화한다. DB를 되돌리기 어려운 변경은 애플리케이션 롤백 가능 범위와 forward fix를 별도로 적는다. 이번 문서 작성은 배포 승인이나 실행을 포함하지 않는다.

완료 보고에는 `검증한 코드/문서 범위 / 실행 명령과 작업 위치 / 성공·실패·skip 건수 / 미검증 범위와 이유 / 남은 위험·다음 조치`를 남긴다. 문서 전용 변경은 링크·규칙 ID·모순·예시·diff 검증으로 완료하고 서버 테스트를 실행했다고 쓰지 않는다.

**검증·완료:** 해당 변경의 필수 검증이 통과하고 미해결 실패가 없을 때만 그 범위의 완료를 선언한다. 네이티브 빌드·실기기·실제 공급자·DB·배포는 각각의 증거가 있을 때만 완료로 표시한다.

## 이직 포트폴리오에 남길 증거

문제 → 선택한 설계 → 검증 → 결과 순서로 남긴다. 예시는 중복 RSS 수집 방지, AI 실패 재처리, 조회 쿼리 개선, 사용자 데이터 분리, 트랜잭션 롤백 테스트다. 금융 뉴스 서비스를 결제·정산·원장 운영 경험으로 표현하지 않는다.
